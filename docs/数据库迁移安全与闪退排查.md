# 数据库迁移安全与闪退排查

> 背景：2026-11-05 用户反馈「更新到 v0.5.9 后一刷新课表就闪退」，并怀疑「每次加新字段就容易闪退」。
> 排查分五轮，共做了六件事：
> ① **SQL 级审计**：把 14→15→16→17 每一步迁移在真实 SQLite 上重放，再与 Room 2.6.1 生成代码里的期望结构逐列比对；
> ② 用**官方包**走真实升级路径（0.5.6 v14、0.5.8 v16 → 0.5.9），确认迁移在真机环境跑得通；
> ③ 人为构造「库结构与代码不一致」的库，**复现 DB 故障被伪装成崩溃**的代码路径；
> ④ **第二轮**用官方 v0.1.5 包（DB3）直跳新版，**复现并修复了一条真实、必现的迁移闪退**（3→4/4→5 的 notNull 漂移），修复方式是链尾新增 17→18「结构自愈」迁移；
> ⑤ **第三轮**在 **Android 10（API29）+ 系统深色模式** 下复现了官方 v0.5.9 的**启动必崩**：布局把颜色状态列表当 Drawable 用，API≤29 的 `ResourcesImpl` 按 `res/color/` 字面前缀判断资源，夜间变体路径不匹配 → inflate 崩溃。已改代码设色 + 删资源 + 加防回归单测（§5.6）；
> ⑥ **第四/五轮**把修复固化成**永久回归 + 诊断闭环**：新增运行期深色冒烟 `MainActivityNightModeTest`（强制夜间模式拉起 `MainActivity`）；CI `androidTest` 改为 **API35 + API29 双机型矩阵**；启动失败弹窗新增**「分享日志」**（一键回传版本/机型/异常栈/最近崩溃，无需 adb）。
>
> 本文结论按「证据状态 + 崩溃类别」看，**不要混用**：
> - **已证明（迁移）**：16→17 迁移 SQL 与 Room 期望结构完全一致；0.5.6/0.5.8 → 0.5.9 升级成功、数据保留；17→18 自愈已修复极老库路径。
> - **已证明（资源兼容，第三轮）**：官方 v0.5.9 在 API29 + 深色模式必崩（§5.6）；修复后 API29 深色/浅色、API35 深色均正常。
> - **已证明（回归/诊断，第四/五轮）**：仪器化在 API29 与 API35 各 **11/11 PASSED**（10 迁移/健康 + 1 深色冒烟）；CI 已改为 API35/API29 双机型矩阵，启动失败「分享日志」实测可拉起系统面板并携带异常栈（§5.7）。
> - **尚未确认**：**用户 0.5.9 的实际崩溃栈仍没拿到**。本轮已确认两类真实、必现的崩溃（极老库迁移 / Android 8~10 深色资源兼容）原因完全不同，不能互相代入；用户这起是哪类、还是第三类，需靠 §7 取证。

## 1. 迁移机制现状

### 1.1 版本号与迁移链

| 项目 | 现状 |
| --- | --- |
| Room 版本 | 2.6.1（`room-runtime` / `room-compiler` / `room-testing` 同版本） |
| 当前 schema 版本 | `LATEST_VERSION = 18`，`@Database(version = AppDatabaseMigrations.LATEST_VERSION)` 直接引用，**版本号单一来源** |
| 迁移条数 | **16 条手写迁移**，覆盖 2→3→…→18；`ALL` 按起始版本升序登记 |
| 最近一步 | `MIGRATION_17_18` 是**「结构自愈」**（不是新增字段）：按标准结构重建 `courses`，把历史迁移造成的可空列/数据漂移收敛掉（见 §3.2、§5.5） |
| 最早支持版本 | `OLDEST_SUPPORTED_VERSION = 2` |
| 破坏性迁移 | 仅 `fallbackToDestructiveMigrationFrom(1)`：版本 1 是上游 WakeUp 课表遗留库，没有迁移路径，重建是唯一出路；**其余版本缺迁移一律抛异常**，不会静默清库 |
| 版本倒挂 | 无 fallback，走同一条 `onUpgrade` 查找迁移路径，找不到就抛异常 |

管理上的两道保险（都在 `app/src/main/java/com/cherry/wakeupschedule/model/`）：

- `AppDatabaseMigrations.LATEST_VERSION` 是版本号的唯一来源，避免「实体改了、迁移写了、version 忘了 +1」；
- `AppDatabaseMigrations.ALL` 必须声明在所有 `MIGRATION_*` 之后（Kotlin 对象属性按书写顺序初始化，提前引用会拿到 null）；`AppDatabaseMigrationsTest`（JVM）校验链非空、首尾相接、只跨一版、升序无重复。**注意：这个测试不执行 SQL。**

### 1.2 schema 快照（迁移链唯一的物证）

`app/schemas/com.cherry.wakeupschedule.model.AppDatabase/` 下现有 **14 / 15 / 16 / 17 / 18** 五个快照：

- `exportSchema = true` 直到 v0.4.3（commit `801f3e1`）才开启，**14 是第一个快照**；
- 2→13 这一段（11 步）迁移**没有任何 schema 快照**，也从未被任何测试执行过，只能靠代码审计（见 §3.4）；
- `app/build.gradle` 已把 `app/schemas` 加进 androidTest assets（`androidTest.assets.srcDirs += files("$projectDir/schemas")`），供 `MigrationTestHelper` 按 `版本.json` 严格校验；
- 17.json / 18.json 的 `identityHash` 同为 `df1e34097c66d822a34e28cca8ddb1df`；18.json 的 `entities` 与 17.json **完全一致**（只有 `version` 变化）——因为 identity hash 只由表结构决定，17→18 自愈重建后的结构与 17/18 的标准结构相同；
- release 构建产物 `app/build/generated/ksp/release/java/com/cherry/wakeupschedule/model/AppDatabase_Impl.java` 当前为 `Delegate(18)`，内嵌 identityHash 同样是 `df1e34097c66d822a34e28cca8ddb1df`（`INSERT OR REPLACE INTO room_master_table (id,identity_hash) VALUES(42, 'df1e…')`），与 18.json 一致。

**约定：快照必须提交。** 少提交一版，那一步迁移就永远无法被 `MigrationTestHelper` 验证。

### 1.3 identity hash 校验原理（为什么「版本号相同、结构不同」也会崩）

Room 在生成 `AppDatabase_Impl` 时，把 **schema 的指纹（identity hash）编译进代码**；建库时写入 `room_master_table`（`id=42`）。打开数据库时（Room 是**懒打开**的：`AppDatabase.getInstance` 只 `build`，第一次 DAO 查询才真正 open / 跑迁移 / 校验）：

| 打开时的情况 | Room 行为 | 失败时的异常 |
| --- | --- | --- |
| 库版本 **低于** 当前版本（正常升级） | 依次执行迁移 → 用**生成代码里的期望结构**逐表逐列校验 → 成功后写回新的 identity hash | `IllegalStateException: Migration didn't properly handle: courses(…)` |
| 库版本 **等于** 当前版本 | **只比对** `room_master_table.identity_hash` 与生成代码里的期望值（Room 2.6.1 同版本不做逐列校验，哈希就是「这份库是否与当前代码同源」的判据） | `IllegalStateException: Room cannot verify the data integrity. Looks like you've changed schema but forgot to update the version number. … Expected identity hash: X, found: Y` |
| 库版本 **高于** 当前版本 / 缺迁移路径 | 走同一条 `onUpgrade` 找迁移路径；找不到（且没有对应版本的破坏性 fallback） | `IllegalStateException: A migration from X to Y was required but not found. Please provide the necessary Migration path …` |
| 没有 `room_master_table`（预置库/被清过） | 用生成代码校验结构 | `IllegalStateException: Pre-packaged database has an invalid schema: …` |

所以「**版本号相同但结构不同**」的后果是：这张库的 identity hash 与代码期望值不一致 → 打开瞬间抛 `Room cannot verify the data integrity`。典型来源：

- 改了实体/迁移 SQL 但**忘了 `LATEST_VERSION` +1**（最常见）；
- 同一 DB 版本下改过实体结构（历史上开发机出现过，见 `MIGRATION_8_9` / `MIGRATION_10_11` 的注释：未发布的实验版表结构残留在开发机）；
- 安装过 DB 版本更高的包，再降级/换渠道包；
- 第三方渠道包、改包签名的「同版本不同内容」包。

**校验时机很重要**：这些异常都在「第一次真正打开数据库」时抛出。`AppInitializer` 的后台初始化通常是进程内第一次打开（`JwxtAccountManager.init` 的首次 DAO 查询），之后主线程/刷新路径再次访问时会**再抛一次**——这就是 §4.2 复现出来的崩溃形态。

## 3. 历史缺陷与现网可达性

### 3.1 3→4 与 4→5 的 notNull 漂移（物证）

| 迁移 | 问题 | 后果 |
| --- | --- | --- |
| `MIGRATION_3_4` | `ALTER TABLE courses ADD COLUMN week_bitmap INTEGER DEFAULT 0`、`course_category TEXT DEFAULT ''`——**没有 `NOT NULL`**；而实体是 Kotlin 非空类型，Room 期望 `NOT NULL` | 迁移后结构与 Room 期望不一致，升级校验抛 `Migration didn't properly handle: courses(…)` |
| `MIGRATION_4_5` | 为加 `semester_id` **DROP TABLE courses 重建**，重建的 6 个列同样不带 `NOT NULL`（`week_bitmap` / `course_category` / `alarm_enabled` / `alarm_minutes_before` / `color` / `cover_image_path`） | 同上；且 **DROP 会丢 DB4 用户的全部课程**（数据丢失） |

提交 `f9f9d75` 当时把「加 `NOT NULL`」改成「移除 `NOT NULL` 以兼容旧版 SQLite」——这个方向是错的：SQLite 支持 `ADD COLUMN … NOT NULL DEFAULT`，移除 NOT NULL 只会造成结构漂移，并不能解决校验问题。

**这不是理论风险**：2026-11-05 第二轮已用官方 v0.1.5（DB3）包直跳复现了必现崩溃，见 §4.5。

### 3.2 现网可达性与修复状态（第二轮已实测复现并修复）

**结论：这不是理论风险。** 2026-11-05 第二轮用官方旧包实测复现了必现崩溃，并已通过 17→18「结构自愈」迁移修复。

| 升级路径（→ 新版） | 结果 |
| --- | --- |

### 4.2 篡改 identity hash 复现崩溃：DB 故障如何被伪装成「刷新时闪退」

在模拟器上人为把 `room_master_table.identity_hash` 改坏（**只在一次性模拟器上做**）：

```bash
adb root    # 模拟器；真机 release 包无 root 不可做
# 方式一：模拟器内直接改（若带 sqlite3）
adb shell "sqlite3 /data/data/com.cherry.wakeupschedule/databases/schedule.db \
  \"UPDATE room_master_table SET identity_hash='deadbeef' WHERE id=42;\""
# 方式二：pull → 本地 sqlite3 改 → push 回去
adb pull /data/data/com.cherry.wakeupschedule/databases/schedule.db /tmp/schedule.db
sqlite3 /tmp/schedule.db "UPDATE room_master_table SET identity_hash='deadbeef' WHERE id=42;"
adb push /tmp/schedule.db /data/data/com.cherry.wakeupschedule/databases/schedule.db

adb shell am force-stop com.cherry.wakeupschedule
adb shell am start -n com.cherry.wakeupschedule/.MainActivity
adb logcat -v threadtime | grep -E 'AppInitializer|Room|FATAL EXCEPTION'
```

实际观察到的顺序：

1. 后台初始化线程第一次打开 DB（`JwxtAccountManager.init` 的首次 DAO 查询）抛 `IllegalStateException: Room cannot verify the data integrity…`；
2. `AppInitializer.runInit` 的 `catch (Throwable)` **记录「后台初始化失败」后吞掉**，App 继续以空数据启动；
3. `MainActivity` 创建 `CourseViewModel` / 页面首次 DAO 查询，**主线程再次触发打开与校验**，同一个异常没人接住 → `FATAL EXCEPTION`，进程崩溃；
4. release 包 logcat 里能看到完整栈（debug/release 都有，release 需按 §7.2 取）。

（上述第 1–3 步是加固前的行为；本轮加固后同样是这个实验，但第 3 步会先弹「本地数据读取失败」恢复弹窗，不再崩到主线程——见 §5.1。）

这个实验说明两件事：**① 数据库故障会被伪装成「启动正常、随后在某个操作时崩」，不能因为「崩在刷新」就断定是刷新代码/迁移 SQL 的问题；② 只要启动期异常被吞、后续 DB 调用又没有兜底，任何 DB 异常最终都会以「闪退」形式暴露给用户。**

### 4.3 崩溃面（加固前的代码路径）与历史两起「刷新闪退」

| 位置 | 加固前的行为 | 后果 |
| --- | --- | --- |
| `AppInitializer.runInit` | `catch (Throwable)` 只 `Log.e("AppInitializer", "后台初始化失败", t)`，失败原因不向上暴露 | 上层不知道 DB 已坏；同一异常在主线程/刷新路径再次抛出 |
| `AppDatabase.getInstance` | 懒打开：只 `build`，首次 DAO 查询才 open / 迁移 / 校验 | 异常抛出点在「谁第一次碰 DB」而不是启动处 |
| `JwxtImportService.fetchAndSaveScheduleForSemester` | 返回 `result.map { 转换 → replaceAllCoursesForSemester → … }`；**`Result.map` 不捕获 transform 内的异常** | 转换/落库异常直接向外抛 |
| `ScheduleFragment.refreshScheduleFromJwxt` | `lifecycleScope.launch(Dispatchers.IO)` 里直接调用上面这行，没有 try/catch；协程内 `requireContext()` 也可能在页面销毁后抛 `IllegalStateException` | 异常逃出协程 → 进程崩溃 |
| `GradeImportService` / `ExamScheduleImportService` | 同样是 `result.map { …落库… }` 在 `doWithAuth` 的 try/catch 之外 | 成绩/考试导入同样可崩 |

已查明的两起「刷新课表闪退」（**都不是迁移 SQL 错误**），加上本轮待确认的一起：

1. **v0.5.7**：R8 合并了 Gson 匿名 `TypeToken` 子类 → 反序列化 `NoSuchMethodError`/类型错误，已由 v0.5.8（commit `a31be55`）修复；
2. **11-04 23:25（debug 包）**：`NoSuchMethodError: Course.copy$default`——加字段后**增量构建产物不一致**（旧 class 调用了新签名的 `copy`），clean 构建即消失；
3. 本轮用户反馈：**待用户日志确认**（§4.4）。

三起都发生在「刷新课表」路径，这就是用户「每次加新字段就容易闪退」观感的来源：加字段 → 构建/混淆/迁移任一环节出错 → 往往在刷新时第一次大量读写 DB 才暴露。

另外还有一类**启动期**迁移校验失败（极老库直跳，§4.5）：它跟「刷新路径」无关，但同样表现为闪退——排查时不要把它和上面三起混在一起。

**复现结果（必现）**：


### 5.5 结构自愈迁移 17→18（第二轮新增）

| 项 | 内容 |
| --- | --- |
| 版本变化 | `AppDatabaseMigrations.LATEST_VERSION` 17 → **18**；`ALL` 末尾登记 `MIGRATION_17_18` |
| 做什么 | 不新增字段，而是**按当前标准结构重建 `courses`**：`DROP TABLE IF EXISTS courses_v18`（幂等）→ `CREATE TABLE courses_v18` → `INSERT INTO courses_v18 (32 列) SELECT COALESCE(列, 默认值) FROM courses` → `DROP TABLE courses` → `ALTER TABLE courses_v18 RENAME TO courses` |
| 为什么能修 | 历史漂移的 6 列重建后变成 NOT NULL + 实体默认值；历史 NULL 数据被收敛为 `0 / '' / 1 / 15`，不会触发 `NOT NULL constraint failed` |
| 标准结构单一来源 | `courses` 的建表 SQL 抽成 `AppDatabaseMigrations.coursesCreateSql(tableName)`，复制列清单 `COURSES_COLUMNS` / `COURSES_COPY_SELECT_SQL` 与它同源；将来再发现历史漂移，新增的自愈迁移复用这套定义 |
| schema 快照 | 新增 `app/schemas/com.cherry.wakeupschedule.model.AppDatabase/18.json`：entities 与 17.json 完全一致、identityHash 同为 `df1e3409…`、仅 `version` 变为 18；release 生成代码为 `Delegate(18)` |
| 不变量 | **没有修改任何已发布迁移**（2→3 … 16→17 原样保留）；正常库只是多跑一步自愈 |
| 验证 | 仪器化套件双 API 各 11/11；设备实测：DB3→v18 不崩且 32 列 NOT NULL、真实 v17→v18 零丢失（§4.5） |

### 5.6 资源兼容性：颜色状态列表不能当 Drawable 用（API≤29，第三轮新增）

> 本轮排查共确认**三类真实崩溃**，原因完全不同，**不要混用**：
> ① v0.1.x（DB3）极老库迁移校验失败 —— 已由 17→18 结构自愈修复（§4.5）；
> ② Android 8~10（API 26–29）+ 深色模式启动资源兼容崩溃 —— 本节，已修复；
> ③ 用户 0.5.9 的崩溃栈 —— **仍待用户日志**（§4.4）。

#### 现象（官方 v0.5.9，Android 10 / API29 + 系统深色，启动必崩）

```log
FATAL EXCEPTION: main
android.view.InflateException: Binary XML file line #22 in layout/activity_main: Error inflating class PillBottomNavView
Caused by: android.content.res.Resources$NotFoundException: File res/color-night-v8/bottom_nav_bg.xml from drawable resource ID
Caused by: org.xmlpull.v1.XmlPullParserException: Binary XML file line #5: <item> tag requires a 'drawable' attribute
    at android.graphics.drawable.StateListDrawable.inflateChildElements(...)
```

#### 根因（AOSP 源码级，API≤29）

- 布局里写的是 `android:background="@color/bottom_nav_bg"`，而这个资源是**颜色状态列表**：`res/color/bottom_nav_bg.xml` 的内容是 `<selector><item android:color="#DDE4ED"/></selector>`；
- API ≤ 29 的 `ResourcesImpl.loadDrawableForCookie` 用**字面前缀**判断颜色资源：
  `if (file.startsWith("res/color/")) { loadColorOrXmlDrawable(...) } else { loadXmlDrawable(...) }`；
- 深色模式走夜间变体，编译后的资源路径是 **`res/color-night-v8/bottom_nav_bg.xml`**（构建工具会给 `night` 限定符补 `-v8`），不匹配 `res/color/` 前缀 → 被当**普通 Drawable XML** 解析；
- `StateListDrawable.inflateChildElements` 要求 `<item android:drawable="...">`，而颜色状态列表写的是 `<item android:color="...">` → 抛 `Resources$NotFoundException`；
- 异常发生在 `View.<init>` 读取 `android:background` 时 → 整个 Activity inflate 失败 → 启动崩溃。**这个阶段没有可用的 try/catch 兜底点**（View 在 `setContentView` 内部构造），只能靠规则 + 测试预防；
- **API 30+ 已改为按资源类型判断**（AOSP Android 11+ 的 `ResourcesImpl` 不再用 `res/color/` 字面前缀），所以 Android 15 开发机/模拟器永远复现不了 —— 典型的「只在用户老系统真机上闪退」。

#### 受影响范围

| 项 | 内容 |
| --- | --- |
| 系统 | **Android 8.0–10（API 26–29）**（本项目 `minSdk=26`），**仅系统深色模式**；浅色模式走 `res/color/` 路径，正常 |
| 入口 | `activity_main.xml` 的 `PillBottomNavView` 背景（`android:background="@color/bottom_nav_bg"`）→ 启动即崩；`fragment_schedule.xml` 的 `overlay_loading` 同款写法（进入课表页时暴露） |
| 引入时间 | 自 v0.3.17 起：`activity_main` 在 commit `9221be9`（2026-07-31，底部导航栏背景对齐）引入；`fragment_schedule` 遮罩在 commit `8f91020`（2026-08-16，三层 loading）使用同款背景 |

#### 修复

1. 两处布局移除 `android:background="@color/bottom_nav_bg"`；背景本来就由代码设置——`MainActivity` 在 `setContentView` 后用 `ColorDrawable(PageBackground.bottomColor(this))`，`ScheduleFragment.onViewCreated` 对 `overlay_loading` 同样设置 → **视觉零变化**；
2. 删除 `res/color/bottom_nav_bg.xml`、`res/color-night/bottom_nav_bg.xml`；经确认无引用后，底栏 tint 用的 `res/color/bottom_nav_color.xml` 也一并删除（仓库当前已无 `res/color*/` 资源。tint 走 `getColorStateList`，本就不受该 Drawable 问题影响；将来需要 tint 状态色可放心在 `res/color/` 重新添加）；
3. 新增防回归单测 `app/src/test/java/com/cherry/wakeupschedule/res/ColorStateListAsDrawableTest.kt`：动态收集 `res/color*/` 下的状态列表文件名，扫描 `res/layout/*.xml`，若 Drawable 类属性（`background` / `src` / `foreground` / `drawableLeft` 等）引用 `@color/X` 且 `X` 是状态列表 → 测试失败；注释里写清了 AOSP 前缀原因。当前仓库没有 `res/color*/` 资源时测试自然通过，**将来一新增 `color*/X.xml`、又被布局当 Drawable 引用就会被拦下**。运行期互补回归见 §5.7（一个查引用、一个真加载）。

#### 验证

#### 开发自检规则（必须遵守）

1. 本项目 `minSdk=26`，用户中仍有 Android 8/9/10 老系统 → 布局改动必须考虑 API≤29；
2. **布局的 Drawable 类属性**（`android:background` / `src` / `foreground` / `drawableLeft/Right/Top/Bottom/Start/End`）**禁止**引用 `res/color*/` 下的颜色状态列表（尤其带 `-night` 变体）；
3. `values/colors.xml` 里的纯色 `@color/xxx` 不受影响；但使用前**先确认**它不是 `res/color*/` 下的状态列表；
4. 需要「随深浅色 / 换配色变化的纯色背景」→ 代码 `ColorDrawable(...)`（本项目 `PageBackground.bottomColor()` 的既有做法），或真正的 `res/drawable*/` 形状/选择器；
5. tint 类属性（`app:tint` / `app:itemIconTint` / `android:backgroundTint` 等）使用颜色状态列表是**正确**用法，不受影响；
6. 改完布局跑 `./gradlew :app:testDebugUnitTest`（`ColorStateListAsDrawableTest` 自动拦截引用问题）；深色/资源类改动还要跑 `connectedDebugAndroidTest`——CI 在 **API35 + API29** 双机型跑，内置 `MainActivityNightModeTest` 深色启动冒烟（Android 15 开发机本地无法复现 API≤29 的此类问题）。

## 6. 加新字段的标准动作（必须按顺序）

`app/schemas/` 是 Room 导出的结构快照，**必须提交**。改实体时按这个顺序走（与 `CONTRIBUTING.md` 的「数据库迁移约定」一致）：

1. **改实体**。新增字段若是 Kotlin 非空类型，必须在实体上声明 `@ColumnInfo(defaultValue = …)`（例如 `defaultValue = ""` / `"0"`），迁移 SQL 对应写 `… NOT NULL DEFAULT …`；可空字段用 `?`。
2. **`AppDatabaseMigrations.LATEST_VERSION` + 1**（当前为 `18`）。
3. **新增 `MIGRATION_N_N1` 并登记进 `AppDatabaseMigrations.ALL`**（`ALL` 必须声明在所有 `MIGRATION_*` 之后；链必须首尾相接、只跨一版）。
4. **构建一次**（KSP 生成新 schema）→ 把 `app/schemas/com.cherry.wakeupschedule.model.AppDatabase/<新版本>.json` **连同代码一起提交**。
5. **在 `AppDatabaseMigrationTest` 补一条 `runMigrationsAndValidate`**：至少覆盖「上一版 → 新版」+「带一行旧数据升级」；维护好 14→LATEST 全链用例（有快照的起点才算数）。17→18 的「脏库自愈」用例是自愈类迁移的范例。
6. **跑测试**：
   ```bash
   GRADLE_USER_HOME=/home/laoin/.gradle ./gradlew :app:testDebugUnitTest --offline
   # 迁移真 SQL（需要模拟器/真机）
   GRADLE_USER_HOME=/home/laoin/.gradle ./gradlew :app:connectedDebugAndroidTest
   ```
7. **发布前自检**（release 前必须全绿）：
   ```bash
   # a) 快照没有未提交变更（两条都要为空：前者查 tracked 修改，后者连未跟踪的新 JSON 一起查）
   git diff --exit-code app/schemas     # 无输出 = 通过
   git status --porcelain app/schemas   # 无输出 = 通过
   # b) 版本号/哈希一致：LATEST_VERSION == 最新 JSON 的 version；最新 JSON 的 identityHash == 生成代码里的期望哈希
   grep -o 'LATEST_VERSION = [0-9]*' \
     app/src/main/java/com/cherry/wakeupschedule/model/AppDatabaseMigrations.kt
   grep -E '"version"|"identityHash"' \
     app/schemas/com.cherry.wakeupschedule.model.AppDatabase/18.json   # ← 改成新版本号
   grep -o "VALUES(42, '[0-9a-f]*'" \
     app/build/generated/ksp/release/java/com/cherry/wakeupschedule/model/AppDatabase_Impl.java
   # c) 快照齐全：14..LATEST 每个版本都有 JSON
   ls app/schemas/com.cherry.wakeupschedule.model.AppDatabase/
   ```
8. **禁止事项**：
   - **不要修改已发布版本的迁移 SQL 和 schema 快照**（它们是历史事实；对已经升级过的用户库无效，只会让「哪份代码产出哪份结构」不可追溯）。要修只能追加新迁移；
   - **不要**用 `fallbackToDestructiveMigration()`（无参）或放宽其他版本的破坏性 fallback——只对版本 1 保留；
   - **不要**改成 AutoMigration：这条链里有 DROP 重建、条件补列、数据对调、多代同名 schema，AutoMigration 表达不了，且它同样依赖快照与测试；
   - **不要**只跑 `testDebugUnitTest` 就发版（它不执行迁移 SQL）；
   - 升级 Room 版本也要重跑迁移测试，不要假设 identity hash 不变。

**补充约定（历史漂移只能自愈）**：如果发现**已发布的历史迁移**造成了结构漂移（如 3→4/4→5 的 notNull 漂移），**不要改老迁移**，在链尾新增一条「自愈」迁移：按当前标准结构重建表 → `COALESCE` 把历史 NULL 收敛成实体默认值 → `INSERT SELECT` 整行搬迁 → `DROP` → `RENAME`（先 `DROP TABLE IF EXISTS` 临时表保证幂等）。`courses` 的标准建表 SQL 唯一来源是 `AppDatabaseMigrations.coursesCreateSql(tableName)`；再发现历史漂移，按 17→18 的方式在链尾加一步。

## 7. 用户报闪退时的取证步骤

### 7.1 先向用户确认这些信息

| 问题 | 为什么关键 |
| --- | --- |
| 安装/更新方式（应用内更新 / 官网 APK / 渠道包）与更新前版本号 | 判断是否跨版本、是否渠道包/签名不一致 |
| 是覆盖安装还是卸载重装 | 覆盖安装才带着旧库，才可能触发迁移/旧库状态问题 |
| 是否从很早的版本（v0.1.x / v0.2.x / v0.3.x / v0.4.x / v0.5.x）直接升上来 | §3.2 的极老库路径需要这里确认（v0.1.x 直跳是已知会崩的一类，v18 已修） |
| 之前是否装过更高版本、是否降级过 | 版本倒挂会抛 `A migration from X to Y was required but not found` |
| 崩溃是否稳定复现？点「刷新课表」前做了什么（冷启动首次刷新 / 已用一段时间 / 切换学期） | 区分「启动期问题」与「运行期数据/解析问题」 |
| 是否出现「本地数据初始化失败」弹窗（本轮新增） | 出现即说明启动期 DB 初始化失败（§5.1）；让用户直接点弹窗里的**「分享日志」**回传完整诊断（§5.7，无需 adb） |
| 机型、Android 版本、存储空间；能否提供截图/录屏 | 环境类问题（存储满、SQLite 损坏）只能这样发现 |
| 系统是否深色模式？Android 版本是否 8.0–10（API 26–29）？ | 资源兼容类崩溃（§5.6）只在 **API≤29 + 深色模式**复现；Android 11+ 或浅色模式下会「看起来正常」 |

### 7.2 取崩溃栈（四种来源，按可得性排序）

**① 恢复弹窗「分享日志」（第四/五轮新增，用户零门槛，最推荐）**：如果用户看到「本地数据初始化失败」弹窗，点 **「分享日志」** 即可把 版本 / Android 版本 / 机型 / ABI / 时间 / 初始化异常完整栈 / 最近一次崩溃落盘内容 拼成纯文本，拉起系统分享面板（`Intent.ACTION_SEND` + `text/plain`，无需 FileProvider、无需 adb）。让用户直接转发给开发者即可。

**② 应用内崩溃日志文件（本轮新增）**：让用户把下面两个文件之一发回来：

- `Android/data/com.cherry.wakeupschedule/files/crash/last-crash.txt`（外部私有目录，文件管理器可见；Android 11+ 部分文件管理器限制访问 `Android/data`，可用第 ③ 种）；
- 内部私有目录 `filesDir/crash/last-crash.txt`（debug 包可用 `adb exec-out run-as com.cherry.wakeupschedule cat files/crash/last-crash.txt` 取）。

**③ adb logcat**（release 包可看，需用户开 USB 调试）：

```bash
adb logcat -v threadtime -d > logcat.txt
# 只看关键行
adb logcat -d -v threadtime | grep -E \
  'AppInitializer|CrashLogger|Room|Migration didn|FATAL EXCEPTION|SQLiteException|identity|后台初始化失败|Resources\$NotFoundException|InflateException|color-night'
```

**④ 已经发生过的崩溃（不用让用户原地复现）**：

```bash
# 系统 crash 记录（模拟器/可 root 的设备可用；会保留最近的崩溃栈）
```

### 7.3 看到这些关键字，按表判定

| 栈/日志中的特征 | 判定 | 下一步 |
| --- | --- | --- |
| `Room cannot verify the data integrity` / `Expected identity hash: … found: …` | 库结构/哈希与当前代码不一致：同版本改过实体、脏库、渠道包、降级 | §7.4 取库核对 `user_version` 与 `room_master_table`；确认后可用「重置本地数据」恢复，并把库/日志回传 |
| `Migration didn't properly handle: <表>(<实体>)` | 迁移执行了，但结果结构与实体期望不符（NOT NULL/默认值/列缺失等）。**v0.1.x 极老库直跳即此条**，v18 起已由 17→18 自愈修复 | 用 §2.1 的 SQL 级方法复算该步迁移；查库 `user_version`（停在 3/4 且是极老库 → 历史漂移）；确认是历史缺陷还是新加迁移写错 |
| `A migration from X to Y was required but not found` | 缺迁移路径：版本号跳变、版本倒挂、渠道包 DB 版本更高 | 核对崩溃时的应用版本与库的 `user_version`；不要在不了解的情况下装低版本包 |
| `Pre-packaged database has an invalid schema` | 无 `room_master_table` 的预置库结构与代码不符 | 排查是否预置/替换过 DB 文件 |
| `NoSuchMethodError … copy$default` / `Course.copy` | 增量构建产物不一致（类签名新旧混用），不是用户数据问题 | 用 clean build 的包验证；发干净包 |
| `TypeToken` / `JsonIOException` / Gson 相关，且只 release 崩 | R8 合并/裁掉了反射用类（v0.5.7 教训） | 用 `mapping.txt` 反混淆，检查 `proguard-rules.pro` 的 keep 规则 |
| `SQLiteException: disk I/O error` / `database or disk is full` / `database disk image is malformed` | 存储满 / 库文件损坏 | 让用户清理空间；确认损坏后走「重置本地数据」 |
| `后台初始化失败` 后面跟着任意异常 | 启动期 DB/初始化失败。加固后还会弹出「本地数据初始化失败」并给出**重置 / 分享日志 / 退出**入口；加固前只会空数据启动，异常可能在主线程再抛一次 | 看紧随其后的 `FATAL EXCEPTION` 是否是同一异常；按具体异常归类；若弹出恢复弹窗，让用户点「分享日志」回传（§5.7） |
| `InflateException` / `Resources$NotFoundException` / `res/color-night-v8/…` / `<item> tag requires a 'drawable' attribute` | **资源兼容性崩溃**：布局的 Drawable 属性引用了颜色状态列表，在 API≤29 + 深色模式下被当普通 Drawable 解析（§5.6）。**发生在 Activity inflate 阶段，运行时 try/catch 接不住**，只能靠兼容性规则+单测预防 | 对照出错布局的 `android:background` / `src` 等是否引用 `@color/X` 且存在 `res/color*/X.xml`；改为代码 `ColorDrawable` 或真正的 drawable 资源；跑 `ColorStateListAsDrawableTest`；兼容性回归用 API29 深色 |

### 7.5 判定流程（速查）

1. 有崩溃栈 → 先查 §7.3 关键字 → 命中 `Room`/`Migration` → 按 §7.4 取库 + §2.1 复算迁移；
2. 无栈、只有现象 → 先让用户取 §7.2 ①/②/③；同时确认 §7.1 的安装/版本信息；
3. 只在 release 崩、debug 不崩 → 优先按 R8/Gson 方向（`mapping.txt` 反混淆），v0.5.7 有先例；
4. 装 debug 包能复现 → 直接 `adb logcat`/dropbox 拿栈，别猜；
5. 崩在启动 / Activity inflate，栈含 `InflateException` / `Resources$NotFoundException` → 优先查资源兼容性（§5.6），不要先去查数据库。
