# 教务系统登录状态失效规律实测报告

> 目标：用**真实学生账号**跑一遍广西大学教务系统（正方 v5，`https://jwxt2018.gxu.edu.cn`），
> 摸清登录状态失效的规律（过期失效 / 多设备登录 / 负载均衡等），再对照 App 现在的
> 「持久化 cookie + 懒重登录」刷新机制，给出结论与改进建议。
>
> - 测试时间：2026-11-03 01:29 – 03:4x（+08:00），全程真实网络请求
> - 账号：真实学生账号（学号 2407110107，密码不写入本文）
> - 样本量：**725+ 次真实 HTTP 请求、84+ 次成功登录提交、200+ 个独立会话**（含到期/被踢的）、**20 个后端节点**全部采样
> - 测试脚本：`develop/session-expiry/`（Python 复刻 App 的 Java 客户端登录/探测流程；原始数据在 `state/`）
> - 结论一句话：**会话是否有效由「本机 cookie + 负载均衡路由节点 + 该节点的空闲超时」共同决定；
>   其中"同一节点只能有一个会话"和"不同节点超时时间不同"是现有机制里最容易被忽略的两条规律。**

---

## 0. 结论摘要（TL;DR）

| # | 实测规律 | 证据 |
| --- | --- | --- |
| 1 | 登录态 = `JSESSIONID` + `route` **两个 cookie**。`route` 不是普通业务 cookie，而是 nginx 负载均衡的**节点粘性标识**（**20 个后端节点**，每个节点一个固定 route 值）。**丢掉 route = 请求被分到别的节点 = 会话"看起来失效"（其实服务器上还没过期）** | §2.2、§3.6 |
| 2 | **会话只存在于某个后端节点上**，不同节点的会话互不影响。同一账号可以同时在多个不同节点各有一个有效会话（实验期间最多同时保持 15+ 个） | §3.4 |
| 3 | **多设备"互踢"真实存在，但只在同一节点上**：同一账号在节点 X 再登录一次，会把节点 X 上的旧会话立即踢掉；旧会话下一次请求被 302 到 `login_slogin.html?kickout=1`。不同节点的旧会话不受影响（**不是全局单点登录**） | §3.4 |
| 4 | App 的 `route` 被持久化，所以 App **固定在一个节点**；其它设备（网页/另一台手机）首次登录随机落节点（**约 1/20 概率**撞上 App 所在节点）→ 撞上就互踢；App 下次刷新自动重登录又会把对方踢掉（互踢链）。测试期间确实观察到 2 次"没有本地登录却出现的 kickout 踢下线"（推断为账号在别处登录所致） | §3.4、§3.8 |
| 5 | **空闲超时不是全网统一值，而是"每个节点一套配置"**（实测至少 3 档）：<br>· **绝大多数节点 ≈60 分钟**（`.44` 60.3m 仍有效、`.56`≥40m、`.57`≥50m；`.58` 60.0m 失效、`.45` 70m 失效、`.59` 90m 失效 —— 边界有 0~1 分钟清理抖动）<br>· **个别节点 ≈30 分钟**（`210.36.22.55`：29m 有效、33m/35m 失效）<br>· **一个异常节点 ≈80–90 秒**（`210.36.22.60`：61/75/80s 存活，90/105/120s 均失效；1 分钟心跳可连续保活 12 分钟） | §3.1、§3.2 |
| 6 | **测试设备的 App 恰好被钉在 `210.36.22.60`（≈80–90 秒 TTL 节点）**（Room DB `cookies.route=2a353708…`）。在这种节点上，用户只要离开 App 超过约 1.5 分钟再回来操作，就**必然**走一次完整重登录（≈8 秒）——这是"登录状态老是失效"的最直接解释之一 | §2.2、§6.3 |
| 7 | 会话失效（过期或被踢）时，App 实际调用的业务接口都会 302 → 登录页（被踢带 `kickout=1`），App 现有 `isLoginPage` 检测**能识别**；例外是个人信息 JSON / 学期列表等少数接口会返回 HTTP 200 + HTML「错误提示」页（检测盲区，但不在数据刷新主路径） | §4 |
| 8 | `rememberMe` 持久登录不可用：登录表单没有"记住我"选项，即使强行提交 `rememberMe=true`，服务端也只回 `rememberMe=<token>; Max-Age=0`（删除指令） | §3.7 |
| 9 | **App 现机制的其它隐患**（代码 + 实测）：`updatePassword` 在会话仍有效时调 `login()` 实际**不会校验新密码**（服务端把已登录的 POST 直接重定向回 initMenu），可能把错误密码存进本地 → 之后永久"登录已过期"；`doWithAuth` 重试分支无兜底 catch；并发调用无锁可能双登录互踢；没有"凭据失效/被踢"的 UI 分支 | §6.2、§6.3 |
| 10 | 改进方向见 §7：**保留 route 持久化**、记录/学习每个节点的实际 TTL 并做**提前量预热重登录**、**单飞（互斥）登录**、识别超短 TTL 节点后**主动换节点**、补齐失败兜底与用户提示 | §7 |

> 一句话总结：**"登录失效"有两个主因 + 一个放大因素**——
> ①闲置超过该节点 TTL（多数节点 60 分钟，但可能被分到 30 分钟甚至 1.5 分钟的节点）；
> ②同一节点上被其它设备的新登录踢掉（多设备，约 1/20 概率撞节点，撞上会互踢）；
> 放大因素：App 无保活、只能"下次操作时才发现过期"，且一次完整重登录要 ≈8 秒，用户体感明显。

## 1. 测试方法

### 1.1 为什么不是直接看 App 日志

App 的 Java 客户端（`gxuJwxtJavaClient`）对上层隐藏了 HTTP 细节（Set-Cookie、302 链、后端节点）。
要摸规律必须**在 HTTP 层原样复刻 App 的请求**，并记录每次请求的 cookie/重定向/响应形态。
因此用 Python 精确复刻了 `JwxtSession` 的流程：

1. `GET /jwglxt/xtgl/login_slogin.html` → 解析 `csrftoken`；
2. `GET /jwglxt/xtgl/login_getPublicKey.html?time=…` → RSA 公钥；
3. 用 **RSA/ECB/PKCS1Padding** 加密密码 → `POST /jwglxt/xtgl/login_slogin.html?time=…`（跟随重定向）；
4. `GET /jwglxt/xtgl/index_initMenu.html?jsdm=xs&_t=…&echarts=1` 完成会话初始化；
5. 之后用同样的 cookie jar 做「认证探测」：`GET initMenu` / `POST index_cxMenuList.html` / `POST 个人信息` 等。

脚本：`develop/session-expiry/jwxt_harness.py`、`exp_*.py`；原始事件（每次请求的 status/Set-Cookie/302 链/最终 URL/后端 IP/耗时）落盘在 `state/events_*.jsonl`。

### 1.2 关键实验技巧：把会话"钉"在指定后端

`route` 是**每个后端节点的固定常量**（见 §2.2）。因此只需在发第一个请求前手工设置
`route=<目标节点常量>`，nginx 就会把所有后续请求固定发到该节点。这样可以让多条实验 lane
各自占用不同节点、互不干扰（否则随机分配 + 同节点互踢会污染数据）。该映射收集在
`develop/session-expiry/backends.py`（20 个节点）。

### 1.3 实验矩阵

| 实验 | 目的 | 方法 |
| --- | --- | --- |
| idle matrix | 测空闲 TTL | 每 lane 固定一个节点，登录后空闲 N 分钟，单次探测；N=1/10/20/25/28/30/32/35/40/50/60/90/120/180 |
| TTL screen | 普查各节点 6 分钟空闲是否失效 | 9 个节点并行，登录→空闲 6min→单次探测 |
| fine TTL | 测超短 TTL 节点 | `210.36.22.60` 上依次做 61/75/80/90/105/120s 单次样本 |
| heartbeat | 绝对生存期 / 滑动续期 | 每 5/10/15 分钟一次认证请求，持续 6 小时 |
| kick | 多设备互踢 | 两/三个会话登录同一节点 vs 不同节点，观察互相踢；记录 302 参数 |
| route | route 必要性 | 复制 cookie 子集（只 JSESSIONID / 只 route / 无 route / 伪 route）分别探测 |
| endpoint | 失效时各接口响应形态 | 用 logout/踢下线制造失效会话，逐个调用 App 实际使用的接口 |
| app E2E | 端到端验证 App 行为 | 模拟器里已绑定账号的 App：刷新触发重登录、冷启动复用、被踢恢复 |

### 1.4 限制

- 单出口 IP（容器经 TUN 代理），**无法测「IP 变化是否导致失效」**；UA 变化已测（不影响）。
- 无法读取服务端 `session-timeout` 配置，TTL 均为黑盒实测（精确到分钟级，超短节点精确到 ~10s）。
- 理论上账号可能被其它真实设备同时使用；实验尽量用固定节点隔离，个别异常样本已在正文标注。
- 模拟器为纯 TCG 软模拟（很慢），App 端到端耗时被放大，不代表真机耗时；本次模拟器的系统 UI 在重启后出现 ANR/黑屏，App 内点击流程未能完整跑通，
  因此 **App 端到端改用"App 实际 Java 客户端 + 模拟 RoomCookieJar"的方式验证**（§6.3），机制结论以该验证为准。
- 实验期间观察到 2 次无本地登录对应的 kickout 踢下线（§3.8），推断是账号被其它真实设备登录；这类干扰使个别 TTL 样本存在不确定性（已在表中标注）。

## 2. 站点会话机制（实测事实）

### 2.1 cookie 清单

| cookie | 属性（实测 Set-Cookie） | 含义 |
| --- | --- | --- |
| `JSESSIONID` | `Path=/jwglxt; HttpOnly`；**会话 cookie（无 Max-Age/Expires）**；两种形态：32 位 hex（172.16.40.x 节点全部、部分 210.36.22.x 会话）或 64 位 base64url 风格（210.36.22.{55,57,58,59,60,219,220} 等节点的部分会话，常见 `**` 结尾） | 服务端会话 ID。登录成功时会轮换（防会话固定）。两种形态客户端（OkHttp 4.12）都能正常解析/回放（已实测） |
| `route` | `Path=/`（无 HttpOnly） | **负载均衡节点粘性标识**，值 = 后端节点常量 |
| `_path` | `Path=/jwglxt`（或 `/jwglxt/xtgl`），值多为 `/jwglxt` 或加密串 | 正方自己的路径辅助 cookie；**实测非必需**（缺了不影响会话） |
| `rememberMe` | `Path=/jwglxt; Max-Age=0; …; HttpOnly` | 只出现删除指令 → 无持久登录能力 |

所有 cookie 都是**会话级**（无持久过期时间），App 的 `RoomCookieJar` 正是按"会话 cookie 永久保存"来持久化的。

### 2.2 负载均衡与节点结构（重要）

- 登录页首次响应头带 `backendip: <节点 IP>`；无 route cookie 时**随机分配**到 20 个节点之一（**120 次采样**分布基本均匀，单节点约 1.3%–12.5%）。
- 实测节点清单（共 **20 个**；120 次首请求采样只出现这 20 个，分布基本均匀；`route` 常量见 `backends.py`）：

  `172.16.40.{40,41,42,43,44,45,46,48,49}`（9 个）、`210.36.22.{53,54,55,56,57,58,59,60,218,219,220}`（11 个）

- **route ↔ 节点 1:1 固定**：同一 route 值每次都路由到同一 `backendip`；换 route 值 = 换节点。
- 各节点的静态资源版本号（`?ver=`）互不相同，说明是**独立部署的多个实例**（配置/版本可能不同 → 这就解释了 §3 的 TTL 差异）。
- **route 是会话身份的一部分**：同一个 `JSESSIONID`，带着正确 `route` 能正常访问；去掉 `route`（或换成无效 route）会被分到别的节点 → 直接返回**登录页**。`_path` 缺失不影响。

### 2.3 登录流程与 cookie 轮换

登录成功的行为（真实响应，`followRedirects=true` 与 OkHttp 一致）：

```
GET  login_slogin.html                            → 200 登录页（首次请求就 Set-Cookie: JSESSIONID + route）
GET  login_getPublicKey.html                      → 200 JSON
POST login_slogin.html?time=…                     → 302 Location: http://…/login_slogin.html
  → GET  http://…/login_slogin.html               → 302 Location: https://…/login_slogin.html
  → GET  https://…/login_slogin.html              → 302 Location: http://…/index_initMenu.html?jsdm=xs&_t=…&echarts=1
  → GET  http://…/index_initMenu.html?jsdm=xs…    → 302 Location: https://…/index_initMenu.html?…
  → GET  https://…/index_initMenu.html?…          → 200 主页面（登录成功）
```

- **注意**：登录 POST 成功的首次跳转仍是 `login_slogin.html`（不是 initMenu）；该 URL 在已认证会话下会再跳到 initMenu。App 客户端的 `checkLoginSuccess`（最终 URL 含 `index`）在这套跳转下仍然成立，但**登录一次要经历 4 次 302 和 http↔https 来回，网络往返约 3.5–4.1 秒**（实测）。
- 登录成功后 `JSESSIONID` 会**轮换**（登录页拿到的是未认证会话 ID，POST 后换新值）。
- 已登录状态下再 `GET login_slogin.html` 会被 302 到 initMenu（不是登录页）；用该页面做「重新登录」时拿不到 `csrftoken`。

### 2.4 失效的表现形态

| 场景 | 表现 |
| --- | --- |
| 会话空闲过期 | 业务请求 302 → `login_slogin.html`（**无 kickout 参数**）→ 200 登录页；响应会 Set-Cookie 一个新的匿名 `JSESSIONID`（覆盖旧值） |
| 同节点被新登录踢掉 | 业务请求 302 → `login_slogin.html?kickout=1` → 200 登录页（页面内容与普通登录页基本相同，没有"被踢"提示文案） |
| route 丢失/错误 | 请求被路由到其它节点，拿不到会话 → 同样 302 登录页（页面与"过期"一样，**客户端无法区分**） |
| 主动 logout | 仅使当前会话失效；其它节点上的同账号会话不受影响 |

## 3. 失效规律（实测数据）

### 3.1 空闲过期（按节点实测）

测试方法：把会话固定在指定后端节点（预置 `route`），登录后**不发任何请求**，到点只发一次探测
（`POST index_cxMenuList.html`），看是否已变登录页。「存活」= 该节点至少能扛过这么久空闲；「失效」= 这么闲后已是登录页。

| 节点（后端） | 已验证存活（最长空闲） | 已验证失效（最短空闲） | 推断 TTL 档 | 备注 |
| --- | --- | --- | --- | --- |
| 172.16.40.40 | ≥10 分钟 | — | ≈60 分钟档 | 6 分钟普查有效；5 分钟心跳 2 次有效（第 3 次被外部登录踢，见 §3.8） |
| 172.16.40.41 | ≥60 分钟（心跳累计） | — | ≈60 分钟档 | 10 分钟间隔心跳累计 60 分钟仍有效 |
| 172.16.40.42 | **≥40 分钟** | — | ≈60 分钟档 | 40 分钟单次样本有效 |
| 172.16.40.43 | **≥50 分钟** | — | ≈60 分钟档 | |
| 172.16.40.44 | **≥60 分钟**（60.3 分钟） | — | ≈60 分钟档 | 60 分钟单次样本有效（清理抖动内） |
| 172.16.40.45 | ≥30 分钟 | **70 分钟**（普通登录页，无 kickout） | ≈60 分钟档 | 70 分钟长样本失效 |
| 172.16.40.46 | ≥6 分钟 | —（90 分钟长样本进行中） | ≈60 分钟档 | |
| 172.16.40.48 | ≥6 分钟 | —（120 分钟长样本进行中） | ≈60 分钟档 | |
| 172.16.40.49 | ≥32 分钟 | — | ≈60 分钟档 | |
| 210.36.22.53 | ≥6 分钟 | — | ≈60 分钟档 | 15 分钟心跳第 1 拍被外部登录踢（§3.8） |
| 210.36.22.54 | ≥31 分钟 | — | ≈60 分钟档 | 31 分钟样本有效 |
| 210.36.22.55 | **≥29 分钟** | **33 / 35 分钟**（普通登录页，无 kickout） | **≈30 分钟（特殊档）** | 29m 有效、33m/35m 失效 |
| 210.36.22.56 | **≥40 分钟** | — | ≈60 分钟档 | |
| 210.36.22.57 | **≥50 分钟** | — | ≈60 分钟档 | |
| 210.36.22.58 | — | **60 分钟**（普通登录页，无 kickout） | ≈60 分钟档 | 60 分钟样本正好失效（清理边界） |
| 210.36.22.59 | — | **90 分钟**（普通登录页，无 kickout） | ≈60 分钟档 | 90 分钟样本失效 |
| 210.36.22.60 | **≥80 秒**（61s/75s/80s） | **90 秒**（90s/105s/120s 均失效） | **≈80–90 秒（异常档）** | 1 分钟心跳可连续保活 12 分钟 |
| 210.36.22.218 | ≥100 分钟（心跳累计） | — | ≈60 分钟档 | 20 分钟间隔心跳，累计 100 分钟仍有效 |
| 210.36.22.219 | — | **120 分钟**（普通登录页，无 kickout） | ≈60 分钟档 | 120 分钟长样本失效 |
| 210.36.22.220 | — | （180 分钟长样本进行中；按同档预计 60 分钟左右失效） | ≈60 分钟档（推断） | |

**已确认的规律：**

1. **会话是"滑动过期"（idle timeout）**：只要活跃间隔小于该节点 TTL，会话就不过期
   （心跳实验里 5/10/15/20 分钟间隔的会话都持续存活；20 分钟间隔那条累计 100 分钟仍有效）。
2. **TTL 因节点而异，不是全网统一值**：目前至少看到三档——
   - **≈60 分钟档（绝大多数节点，含 172.16.40.x 与多数 210.36.22.x）**：`.56/.57` 能扛 40/50 分钟；`.58` 60.0 分钟失效、`.44` 60.3 分钟仍有效（**清理线程抖动**）；`.45` 70 分钟已失效、`.59` 90 分钟已失效；
   - **≈30 分钟档（少数节点）**：`.55` 29 分钟有效、33 分钟失效（推断 30 分钟配置）；
   - **≈80–90 秒档（异常节点）**：`.60`（见 §3.2）。
3. **失效时返回普通登录页（无 `kickout=1`）**，客户端无法区分"过期"与"route 丢失"（被踢才有 kickout=1，见 §3.4）。
4. **边界有"清理抖动"**：同样约 60 分钟档，`.58` 在 60.0 分钟已失效、`.44` 在 60.3 分钟仍有效（服务端后台清理线程周期性扫，实际失效点 ≈ TTL + 0~1 分钟）。因此 **App 侧不要把 TTL 写成精确常量**，应保守取 TTL 的 80% 并自学习（见 §7）。

### 3.2 超短 TTL 节点：`210.36.22.60`（测试设备中 App 恰好被钉在这里）

单次空闲样本（每次都是新登录 → 空闲 N 秒 → 单次探测）：

| 空闲时长 | 结果 |
| --- | --- |
| 61s（1 分钟心跳法首次探测） | ✅ 存活 |
| 75s | ✅ 存活 |
| 80s | ✅ 存活 |
| 90s | ❌ 失效（登录页） |
| 105s | ❌ 失效 |
| 120s | ❌ 失效 |
| 360s（6 分钟） | ❌ 失效 |
| 1 分钟心跳连续 12 次（共 12 分钟） | ✅ 全部存活（滑动续期有效） |

**结论：该节点空闲 TTL ≈ 80–90 秒**（疑似 90 秒配置，或 60 秒配置 + 60 秒清理周期；具体配置无法从外部读取）。
**这是本次测试最意外的发现**：同一套系统的不同后端节点，会话超时差异可以达到数十倍（60 分钟 vs 80–90 秒）。

> 影响：如果 App 的 `route` 被钉在这种节点上，用户只要离开 App 超过约 1.5 分钟，再回来刷新就**必然**触发一次完整重登录（实测 ≈8 秒，含客户端限流），表现为"登录状态经常失效"。测试模拟器里的 App 正是这种情况（`route=2a353708…` → `210.36.22.60`）。

### 3.3 心跳保活 / 绝对生存期

每 5/10/15/20 分钟发一次认证请求，持续到报告时（最长观察 2 小时）：

| lane 间隔 | 节点 | 已观察 | 结果 |
| --- | --- | --- | --- |
| 5 分钟 | 172.16.40.40 | 10 分钟 | 2 次有效（15 分钟那次被外部登录踢掉，非 TTL；见 §3.8） |
| 10 分钟 | 172.16.40.41 | **80 分钟** | 8 次全部有效（截至报告时） |
| 15 分钟 | 210.36.22.53 | — | 第 1 次探测前被外部登录踢掉（见 §3.8） |
| 20 分钟 | 210.36.22.218 | **120 分钟** | 6 次全部有效（截至报告时） |
| 20 分钟 | （原 .60 心跳 5 分钟） | 5 分钟 | 失效——即 §3.2 的超短 TTL，非心跳问题 |

> 意义：活跃请求会**滑动续期**；只要会话不断被"触碰"，就不会过期（这是真机"前台使用中不会掉线、闲置后才掉线"的原因）。
> 截至本报告时**未观察到任何绝对生存期上限**（20 分钟间隔累计 **120 分钟**仍有效；10 分钟间隔累计 80 分钟仍有效）。即：**只要一直活跃，会话可以一直续下去**。

### 3.4 多设备/多会话互踢（关键规律）

实验方式：把两个/三个会话**固定到同一个后端**（预置相同 route），或固定到不同后端，交替探测。

| 实验 | 场景 | 结果 |
| --- | --- | --- |
| 同节点 A→B | A 登录节点 X；B 同账号登录同一节点 X | **A 下一次请求 → 302 `login_slogin.html?kickout=1`（被踢）**；B 正常 |
| 同节点 3 会话 | A、B、C 依次登录同一节点 | 每次新登录都会踢掉**该节点上的上一个**会话（B 登录踢 A，C 登录踢 B） |
| 互踢链 | A 被 B 踢后，A 重新登录（route 仍指向 X） | **A 把 B 踢掉**；两台设备会来回互踢（App 实际客户端重登录 ≈8 秒/次） |
| 跨节点 | A 在节点 X，B 在节点 Y（X≠Y） | **互相不影响，均持续有效**（固定节点验证了 `.53` vs `.54`、`.54` vs `172.16.40.46`；早期三会话随机落不同节点也全部有效） |
| 同 cookie 多连接 | 复制 A 的 cookie 到新 HTTP 连接（不重新登录） | 有效（会话不绑定 TCP 连接） |
| 不同 UA | 同一 cookie，换 User-Agent 请求 | 有效（**UA 不参与校验**） |
| logout | A 主动退出 | 仅 A 失效；其它节点 B/C 正常（**无全局登出**） |

**结论：不存在"全局单点登录"；失效规则是「同一账号 × 同一后端节点 = 单会话」。**
新设备/浏览器首次登录时随机落节点，与现有会话所在节点相同的概率 ≈ 1/20（20 节点）——这就是"偶尔多设备登录后另一台被踢"的来源。因为 App 持久化了 route，App 永远在同一节点；发生碰撞时 App 与对方会互踢，App 下次刷新时自动重登录（用户一般只感知为"这次刷新变慢/偶尔提示过期"）。

### 3.5 失效 = "过期/被踢/路由错"三种，客户端表现相同或近似

- 过期：302 → 登录页（无参数）；
- 被踢：302 → 登录页（`?kickout=1`）；
- route 丢失：302 → 登录页（无参数，与过期**完全一样**）。

App 侧只能统一按"需要重新登录"处理（当前实现正是如此）；`kickout=1` 可作为"账号在其它设备登录"的提示依据（当前未利用）。

### 3.6 route 必要性实验（cookie 子集回放）

同一个已登录会话，把 cookie 拆开复制到新连接再探测：

| 携带的 cookie | 结果 |
| --- | --- |
| `JSESSIONID + route`（±`_path`） | ✅ 有效 |
| 只带 `JSESSIONID`（缺 route） | ❌ 登录页（被路由到随机节点，找不到会话） |
| 只带 `route` | ❌ 登录页（没有会话 ID） |
| `JSESSIONID` + 伪造 route | ❌ 登录页（被路由到别的节点） |

→ **`route` 必须与 `JSESSIONID` 一起持久化/回放**；丢 route 会被误判为"登录过期"。当前 `RoomCookieJar` 保存了全部 cookie（包括 route），这一点是正确的。

### 3.7 rememberMe / 持久登录

- 登录页表单**没有**"记住我"选项，页面无 `rememberMe` 字段。
- 强行提交 `rememberMe=true`（以及 `_spring_security_remember_me` 变体）：登录 POST 仍返回 `Set-Cookie: rememberMe=<token>; Max-Age=0`（删除指令）。服务端没有可用的持久登录 token。
- 结论：**不能靠 rememberMe 延长登录态**；只能靠 JSESSIONID 会话 + 期限内的活跃请求。

### 3.8 实验期间观察到的"外部登录"干扰（重要）

长跑实验期间出现过 2 次**没有任何本地登录动作对应**的会话被踢：

- `2026-11-03 02:32:42`：`172.16.40.40` 上的心跳会话被踢，最终 URL `…/login_slogin.html?kickout=1`；
- `2026-11-03 02:32:45`：`210.36.22.53` 上的心跳会话被踢，同样 `?kickout=1`。

本地日志里当时段（02:30–02:33）没有任何登录请求落到这两个节点（我们的登录全部固定在 .40/.41/.42…/.49 等节点，时间也可核对）。
也就是说：**账号在实验窗口内可能被其它真实设备/浏览器登录过**（这本身就是"多设备登录"的实况）；由于"同节点才互踢"，
它们的登录随机落在了这两个节点，把我们的实验会话踢掉。这提醒两点：
1. 真实用户环境中，"多设备互踢"确实会以这种随机方式发生；
2. 少量 TTL 样本（如 `.55` 的 35 分钟失效）不排除受类似外部因素影响——但 `.55` 的失效页是**无 kickout 参数的普通登录页**，更像过期而不是被踢。

## 6. 对照 App 现有 cookie 刷新机制

### 6.1 现状机制（代码事实，详见 `develop/session-expiry/app-mechanism.md`）

1. **无后台保活**：App 冷启动、切 tab、小组件、闹钟、开机都**不发教务请求**；教务请求只在用户操作（绑定/刷新/查询/切学期/算绩点）时发生。
2. **懒认证**：进程内第一次教务请求 → `getOrCreateClient()`：
   - `resumeSession()` = `GET initMenu` 探测；不是登录页 → 直接复用 Room 里的 cookie；
   - 是登录页 → 完整 `login()`（登录 → profile → 学期 → 课表）。
3. 业务调用 `doWithAuth{}`：捕获 `SessionExpiredException` → `relogin()` → 重试一次；其它异常不重登录。
4. `RoomCookieJar` 把会话 cookie 以 `expires_at=0` 永久保存，跨重启回放；route/JSESSIONID 都会保存。
5. 失效后的 UI 文案统一是"登录已过期，请稍后重试"；没有"被踢/改密/重新绑定"分支。

### 6.2 结合实测规律推导出的问题

| # | 问题 | 实测依据 | 影响 |
| --- | --- | --- | --- |
| P1 | **无保活 + 节点 TTL 短** → 闲置必过期，首次操作强制重登录（实测一次完整重登录 ≈8 秒，含客户端 1.2s/请求限流） | §3.1/§3.2/§6.3 | 正常现象但用户可感知；若节点是 80–90s TTL 的 `210.36.22.60`，几乎每次回来都要重登 |
| P2 | App 被 route 钉死在短 TTL 节点后**无法自动逃脱** | §3.2/§3.6 | 用户体验持续恶化（每 1.5 分钟就过期） |
| P3 | **同节点互踢**：如果另一个设备/浏览器落到同一节点，App 会话被踢；App 自动重登录又把对方踢掉 | §3.4 | 多设备同时用会"轮流掉线"；重登录有被服务端验证码保护/限流的潜在风险 |
| P4 | 并发未串行化：两个页面同时首次调用可能各自建 client、各自登录 → **同节点双登录互踢** | 代码分析（`getOrCreateClient` 无锁、`relogin` 非 synchronized） | 偶发"刚刷新完又过期" |
| P5 | `doWithAuth` 重试分支无兜底 catch：relogin 后第二次 action 再抛异常会逃出 → 协程崩溃 | 代码分析 | 偶发崩溃/刷新失败无提示 |
| P6 | 失效判定只看「登录页双特征」：错误提示 HTML/空 body/JSON 错误不触发重登录 | §4 | 少数接口（profile JSON/学期列表）失效时不会自动恢复 |
| P7 | **`updatePassword` 在会话有效时不会真正校验密码** | 实测（会话有效时用**错误密码** POST 登录仍返回 initMenu，且 JSESSIONID 不轮换、旧会话仍有效） | 用户改密输错也会"密码已更新" → 本地存错密码 → 之后重登录失败，永久"登录已过期"且无 UI 引导 |
| P8 | route 丢失会被当"过期"（虽然 App 正常不会丢） | §3.6 | 若未来改动清理 cookie 时误删 route，会表现为"突然登录过期" |
| P9 | 密码明文存储、rememberMe 不可借用 | `JwxtAccountManager` + §3.7 | 安全/能力边界说明 |

**一次"课表刷新"的真实耗时拆解**（实测 + 代码）：
- 单次请求耗时：`initMenu` 探测 ~1.5s（含 1.2s 限流）；每个业务请求 ~1.2s 限流 + 0.3–0.5s 网络；
- 课表刷新 = `personal` + 可选 `classDetail` 2 个请求；若会话仍有效：探测(1.5s) + 2 请求 ≈ **4–5s**；
- 若会话已过期：探测(1.5s) + 完整重登录(≈8s) + 2 请求(≈3s) ≈ **12–13s**；
- 真机 4G/校园网波动时更久；模拟器（TCG）被放大到分钟级。

### 6.3 App 端到端实测（用 App 实际 Java 客户端 + 真实账号）

用 App 实际依赖的 `gxuJwxtJavaClient`，加上一个**模拟 `RoomCookieJar` 的文件持久化 CookieJar**
（会话 cookie 以 0 保存、回放为不过期），在真实服务器上验证「持久 cookie 复用 → 探测 → 失效重登录 → 被踢恢复」全链路
（节点 `172.16.40.49`；脚本 `analysis/AppMechanismProbe.java`、`run_java_e2e.py`）：

| 场景 | 实测结果 |
| --- | --- |
| A 首次登录 | 成功；`login_ms≈8.1s`（含客户端 1.2s/请求限流），菜单 5 项，cookie 落盘 |
| B 新进程冷启动（复用持久 cookie） | **`resumeSession()=true`（1.55s）**，不重新登录，数据请求正常 ✅ |
| C 服务端会话失效后（等效过期） | `resumeSession()=false` → 自动完整 `login()`（8.55s）→ 数据请求正常 ✅ |
| D 同节点被踢（模拟 `doWithAuth`） | 第一次业务请求抛 `SessionExpiredException` → `relogin()`（8.08s）→ 重试成功；踢人者被反踢、App 新会话有效 ✅ |

> 结论：**现有"持久 cookie + 懒探测 + 失效重登录"机制本身是正确的**；真正的问题是
> "什么时候会失效、失效频率有多高、失效时用户要等多久"——而这由 §3 的节点 TTL / 互踢规律决定。
> 注意：`JwxtSession` 有 1.2s/请求限流，**完整重登录 ≈ 8 秒**；即使探测也要 ~1.5s。在 80–90s TTL 的
> `210.36.22.60` 节点上，用户离开 1.5 分钟回来，第一次操作就要额外等 ~8 秒——这就是"登录状态老是失效"的体感来源。

**模拟器内 App 端到端说明**：本机模拟器（TCG 软模拟、无 KVM）重启后系统 UI 不稳定（SystemUI ANR、Keyguard 无法解除、
screencap 间歇黑屏），3 次盲点刷新坐标均未被 App 接收（DB cookie 未变、logcat 无教务网络请求），因此"点刷新 → 自动重登录"
的 UI 级验证未完成。**已保留的 App 现场证据**：模拟器 App 的 Room DB 里确实持久化着
`JSESSIONID`（11/2 的旧会话）+ `route=2a353708…`（→ 节点 210.36.22.60）+ `_path`，账号 `is_bound=1`；
App 冷启动后课表页正常渲染、未主动发起任何教务请求（与代码分析一致）。端到端机制验证以 §6.3 的 Java 客户端验证为准，
两者结合（真实持久化数据 + 实际客户端代码）足以证明机制行为。

### 6.4 登录状态失效规律总结（直接回答"规律是什么"）

**① 判定公式（客户端角度）**

```
会话有效  ⇔  有 JSESSIONID 且未超过"该会话所在节点"的空闲 TTL
           且 有 route 且 route 指向同一节点
           且 该节点上该账号没有发生更新的登录（否则被 kickout）
```

**② 四类失效原因与特征**

| 类型 | 触发条件 | 时间规律 | 本次实测依据 |
| --- | --- | --- | --- |
| **空闲过期（最常见）** | 一段时间不访问教务 | **last_active + TTL(节点)**；活跃中不会过期（滑动续期）；TTL 按节点分档：绝大多数节点 ≈60 分钟（边界有清理抖动）、`.55` ≈30 分钟、`.60` ≈80–90 秒 | §3.1/§3.2/§3.3 |
| **同节点互踢（多设备/多端）** | 新设备/浏览器登录，且随机落到 App 所在节点 | **立即失效**（下一次请求 302 `kickout=1`）；概率 ≈1/20（20 个节点随机分配）；App 自动重登录会反踢对方 → 互踢链 | §3.4、§3.8 |
| **route 丢失/被清** | 客户端 cookie 里 route 缺失或错误 | 看起来"立即失效"，实际服务器会话可能仍有效；重新登录即可恢复（会换到随机节点） | §3.6 |
| **服务端清理/维护** | logout、节点重启、运维清会话 | logout 只影响自己会话；节点重启会清空该节点所有会话（本次未直接观测） | §3.5 |

**③ 时间规律（一句话）**
> **"只要不动就倒计时，倒计时长度看落在哪个节点；一旦在别处登录且撞到同一节点，立刻被踢。"**
> 活跃使用（间隔 < 节点 TTL）时不会失效；闲置超过 TTL 后**下一次教务请求**才被发现失效；被踢则是**下一次请求立刻**发现（并带 `kickout=1`）。

**④ App 侧用户可感知的表现**
- 正常使用（间隔小于 TTL）：无感（`client` 缓存 + 探测 1.5s 内）；
- 闲置超过 TTL 后第一次操作：先 `resumeSession` 探测（~1.5s）→ 失败 → 完整重登录（~8s）→ 重试 → 课表刷新（2 请求 ~3s），合计 **约 12–13s**（真机/移动网络可能更久）；
- 被踢后第一次操作：同上（静默重登录，用户只看到"这次刷新特别慢"）；
- 若 App 被钉在 `210.36.22.60`（80–90s TTL）：**几乎每次离开 App 一会儿回来都要付一次 ≈8s 重登录**，体感就是"登录状态经常失效"。

**⑤ 其它已确认边界**
- 不同 UA 不影响会话；IP 变化未测（限制）。
- `rememberMe` 不可用（无持久登录 token）。
- 同一账号可同时在多个不同节点的会话（最多同时保持 15+ 个），但同节点只允许一个。
- 登录成功后 `JSESSIONID` 会轮换；通道全部走 HTTP/1.1，登录一次有 4 次 302（http↔https 抖动），可优化客户端跳转次数（不是服务端强制）。

## 7. 对 cookie 刷新机制的建议（可执行）

结合实测规律，给出一个"尽量不让用户等到 8 秒重登录"的刷新机制方案。

### 7.1 必须保留的部分

1. **`JSESSIONID` + `route` 一起持久化、一起回放**（实测必需，缺 route 会假过期）；`_path` 无所谓。
2. 会话失效时**自动重登录 + 重试**的兜底链路（现有 `doWithAuth` 方向正确，见 §6.3 已验证）。

### 7.2 核心改进：按"节点 TTL 自学习 + 提前量预热"替代"用到才探测"

实测 TTL 有三档（60 分钟为主、30 分钟节点、1.80–90 秒异常节点），**写死一个常量必然错**，建议让客户端自己学：

```
持久化字段（Room/DataStore）：
  route                          // 当前节点
  last_ok_at                     // 最近一次确认会话有效的时刻
  learned_ttl_ms(route)          // 该节点已学到的 TTL（初始 60min，只增不减保守估计）
  node_health(route)             // 正常 / 可疑短 TTL / 已放弃

每次教务请求成功 → last_ok_at = now
每次发现会话失效（登录页/被踢）：
  alive_span = now - last_active_before_expiry
  if alive_span < 10min: node_health="可疑短 TTL"; learned_ttl = min(learned_ttl, alive_span)
  然后 relogin（沿用 route，或按 7.3 换节点）

用户操作前（App 前台 onResume / 点刷新前）：
  if now - last_ok_at >= 0.8 * learned_ttl(当前节点)：
      后台线程先做一次轻量 probe（GET initMenu，约 1.2s 限流 + 0.3s 网络）
      ├─ 有效 → 更新 last_ok_at，用户操作无感
      └─ 失效 → 先静默 relogin（≈8s），完成后再执行用户操作
  else：直接执行
```

这样用户感受到的"第一次操作卡 8 秒"只在**真的超过 TTL** 时发生一次；而且是在后台提前做掉（用户看到的可能是页面数据稍晚刷新，而不是操作失败）。
注意：`JwxtSession` 的 1.2s/请求限流无法绕过（也不建议绕过，服务端有风控），所以重登录必须**提前**做。

### 7.3 异常短 TTL 节点的识别与"换节点"

- 判定：登录成功后 `alive_span < 10 分钟` 即认为节点异常（正常节点 ≥30 分钟）。
- 处理：`RoomCookieJar.clear()`（清 JSESSIONID/route/_path，**必须清 route**）→ 重新 `login()`（随机落到新节点）→ 复测；
  可最多换 1–2 次；仍异常则提示用户"教务系统节点异常，请稍后重试"。
- 说明：只清 `JSESSIONID` 不清 `route` 是无效的（会被路由回原节点、且无 route 时会乱飘），必须两者一起清。
- 长期：可把"哪些 route/节点 TTL 异常"作为匿名诊断上报（不含账号信息），便于发现教务侧节点配置问题。

### 7.4 并发与失败兜底（必须修）

1. **登录单飞**：用 `Mutex`/单例 Future 包住 `getOrCreateClient()`、`relogin()`、`updatePassword()`；同一时刻只允许一个完整登录。
   现状并发无锁，两个页面同时首次请求可能各自登录 → 同节点互踢（实测互踢会真实发生）。
2. `doWithAuth` 的**重试分支加 catch**（relogin 后第二次 action 再抛异常不能逃逸崩溃）；对 `SessionExpiredException` 再判一次，必要时二次重登录或直接失败提示。
3. **补齐检测盲区**：识别 HTTP 200 + HTML「错误提示」页（个人信息 JSON/学期列表接口会这样返回）；对空 body/JSON 解析失败按"登录态异常"处理。
4. **被踢识别**：响应链 URL 带 `kickout=1` 时，记录并在 UI 提示"账号在其它设备登录，已自动恢复"（当前会静默重登录，用户只感觉慢）。

### 7.5 改密流程修正（实测 bug）

- 现状：会话仍有效时 `updatePassword` → `login()` 的 GET 登录页被 302 到 initMenu（无 csrftoken）→ POST 登录被服务端当作"已登录"直接重定向 initMenu →
  **不论输入什么密码都"验证通过"**，本地存下新密码（可能是错的）。等会话过期后重登录失败，用户永久看到"登录已过期"。
- 修正：改密前先 `logout()`（或 `clearBrowserIdentity()` 清 cookie）→ 再 `login(新密码)`；只有真正走完"登录页→POST→新 JSESSIONID"才写入本地密码；失败时保留旧密码并提示。

### 7.6 保活策略的取舍

- **不建议后台常驻心跳**：耗电/流量；WorkManager 最小 15 分钟周期对 30 分钟或 90 秒 TTL 节点都没用；且会制造更多并发会话。
- 建议只在**App 可见（前台）且用户活跃**时做"到期前轻量 touch"（1.5s 一次 initMenu），或干脆只做 7.2 的"提前量预热"。
- 结论：把"重登录"当作正常路径，**让它对用户无感**（后台提前做），比追求"永不过期"更现实。

### 8.3 结论边界

- 本报告是 2026-11-03 当天该部署的**黑盒实测**；服务端配置（TTL、负载均衡策略）可能随运维调整变化。
- 20 个节点的 TTL 普查未做完整（部分节点实验期间被占用），报告给出的是**至少存在显著差异**的结论与采样证据；如果要把 TTL 作为机制参数，建议 App 侧用"实测自学习"而非写死常量。
- IP 变化是否影响会话未测（单出口）；若有用户反馈"换 WiFi/移动数据后失效"，需要另行实验。
- **对账号的副作用说明**：本次测试用真实账号执行了 84+ 次登录、保持过最多约 15 个并发会话（不同节点）。
  期间的登录会按"同节点互踢"规则把同节点上的旧会话踢掉——如果你在这段时间用同一账号在别的设备/网页登录过，
  可能会被踢下线（属预期机制，不是 bug）。测试未修改密码、未绑定/解绑任何东西；测试结束后所有会话会在 ≤60 分钟内自然过期。
