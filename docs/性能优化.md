# 性能优化记录：不改 UI / 不改功能 / 不降精美度

> 目标：在**零 UI 变化、零功能变化**的前提下，把低端机上的流畅度做到极致——
> 冷启动不再被同步 I/O 阻塞、课表翻页/每秒刷新不再做重复解析与分配、
> 桌面小组件与后台闹钟不再无意义唤醒。
>
> 约束（本次硬性遵守）：
> 1. 不修改任何 `res/` 资源（layout / strings / colors / dimens / drawable 全部零改动）——
>    静态 UI 定义与改动前逐字节相同；`git status` 可验证无 res 变更。
> 2. 不新增依赖、不改 Manifest、不改 build.gradle（R8 / 资源压缩配置原样）。
> 3. 行为等价性优先：宁可少改，不引入偶现问题。所有"看起来可能省"但无法证明视觉等价的项，
>    统一列入第 6 节「未实施」，不做。

## 0. 结论摘要

| 热路径 | 改动前 | 改动后 |
| --- | --- | --- |
| 冷启动 | `Application.onCreate` 里串行做 4 段同步 Room 查询（首次还触发建库 + 14 版迁移链），随后才进 Splash 空等 400ms；实际等待 ≈ **init + 400ms** | 这 4 段全部挪到 `app-init` 后台线程，与闪屏 400ms、Activity 类加载/inflate 重叠；主线程只在真正需要数据前 `awaitReady` 兜底；实际等待 ≈ **max(400ms, init)** |
| 倒计时（每秒） | 每秒 1 个 `Calendar` + 全量 `filter` + `sortedBy`（比较器里反复 Gson 解析时间表，约 15~40 次/秒）+ 2 遍 `find` + 无条件 `setText`；**App 退后台仍每秒空转** | 每秒：**0 Gson 解析、0 排序、0 filter、0 Calendar 分配**，仅 n 次 int 比较 + 1 次字符串；**页面不可见即停**，可见时 onStart 立即刷新 |
| `TimeTableManager.getTimeSlots()` | 每次调用 = SharedPreferences 读 + Gson 反序列化 13 个对象（每个课表页 bind 一次、倒计时每秒几十次） | 首次解析一次，之后 1 次 `@Volatile` 读；保存/重置在同一把锁内同步刷新缓存 |
| 周课表每页 bind | 每次爆量：全量课程 `filter` + `groupBy(Triple)` + 组内排序 + 每组重读深色模式 + 每次 bind 重设网格色触发整页重绘 + 每卡新 drawable/View + 每次 bind 新建 Calendar/TypedValue | 按周预计算"筛选 + 重叠分组 + 组内排序"（数据变才失效）；网格配置只在重建时间轴时设置；深色/透明度提到循环外；Calendar/TypedValue/当日列 drawable 复用 |
| 切「周课表 ⇄ 总课表」 | 每次重新归并全部课程 | 课程列表引用没变时 0 次归并 |
| 总课表行 bind | 每行 2 个新 `GradientDrawable` | ViewHolder 级复用，只改颜色 |
| App 每秒小组件 tick | 有实例：≈13~16 次 IPC + 1 次 AMS 广播/秒；无实例：每秒 1 广播 + 1 IPC | **无实例 0**；有实例内容未变 **0 IPC/秒**（连 RemoteViews 都不重建），内容变化那一秒 1 次批量提交 |
| 每分钟 TIME_TICK | 4 次广播 + 30+ 次 IPC | 4 次进程内直调 + 4 次批量提交，闹钟目标未变则 0 次 set/cancel |
| 15 分钟兜底刷新 | 每款组件各挂一条 `setInexactRepeating`（最多 5 条，≈480 次唤醒/天） | **1 条共用**（≈96 次/天，-80%），一次醒来刷新所有有实例的组件 |
| 桌面无任何小组件时后台唤醒 | 30 分钟链 + 午夜 + 开机后多条重复闹钟 ≈ **430+ 次/天** | **0 次**（残留旧闹钟醒来一次即自清） |

工程验证：`:app:assembleDebug` 与 `:app:assembleRelease`（R8 + 资源压缩）均通过；
JVM 单测 **110/110 通过**；交付的 debug APK 与改动前**字节数相同**（10,510,146 B）。

## 2. 工作流 A：冷启动与主线程 I/O

### 2.1 设计：后台初始化器 + 就绪闩

新增 `service/AppInitializer.kt`：

```
App.onCreate（主线程，变轻）
  ├─ instance / ActivityLifecycleCallbacks / ThemeModeManager.apply（必须主线程）
  ├─ AppInitializer.start(this) ─────────────► "app-init" 后台线程
  │                                             ├─ SharedPreferences 预热（只读一次）
  │                                             ├─ JwxtAccountManager.init（首次 DB 打开/建库/迁移）
  │                                             ├─ RoomCookieJar.init
  │                                             ├─ SemesterManager.init
  │                                             ├─ CourseDataManager.getInstance（课程缓存/颜色重分配）
  │                                             └─ finally：ready=true → countDown → 主线程就绪回调
  ├─ 小组件闹钟链 / 注册 receiver / 自动主题轮询（主线程，保持原样）
  └─ startSecondTick()：未就绪则就绪后回主线程再启动
```

关键安全约束（全部实现并逐条论证于 `develop/perf/startup.md`）：

- `awaitReady()`：就绪后只是一次 volatile 读；未就绪时**主线程最多等 10s**（防止异常卡死），
  后台线程不设超时；初始化线程自己调用立即返回（**绝不自等**）。
- 初始化线程不 post 主线程、不等待任何依赖主线程的锁 → 主线程在 `awaitReady` 上等待时初始化一定能推进。
- 初始化即使抛异常也会置 ready 并放行：旧实现是 `onCreate` 直接崩，改为记录日志 + 空数据启动（正常路径无影响）。

### 2.2 数据一致性：三扇门

所有读路径在数据就绪前等待，覆盖「不经 Splash 的入口」：

- `MainActivity.onCreate`（setContentView 会立刻创建 NavHostFragment 并跑各页 onViewCreated）、
  `SplashActivity` 400ms 回调里都显式 `awaitReady()`。
- `SemesterManager.getAll/getCurrent/getCurrentIndex`、`JwxtAccountManager.isBound/getUsername/getPassword/getProfile`、
  `CourseDataManager.getInstance` 内部门控。
- 已逐 Activity 核对（GPA / 成绩 / 考试 / 我的 / 绑定 / 小组件接收器 / RemoteViewsService）：
  不存在 NPE 或「按空学期渲染」路径；不读这三个缓存的页面（组件中心 / 时间表 / 外观 / 字体 / 关于）不受影响。

### 2.3 收益

- 主线程同步 DB 查询：**4 段 → 0 段**；SQLite 建库/迁移与课程加载全部与 Splash 窗口重叠。
- 冷启动总耗时从 `init + 400ms` 变为 `max(400ms, init)`，严格不劣于现状。
- 每秒 tick 在初始化完成后才启动，避免未就绪时首刷。
- 小组件刷新链的建立（30 分钟精确链 + 午夜链）也从 `App.onCreate` 主线程挪到初始化线程：
  这两处只做 `AlarmManager` / `AppWidgetManager` 的 binder 调用，原实现每次启动在主线程多付
  8~10 次 IPC；目标触发时刻都在几十分钟后，提前/延后几毫秒挂上无任何可观察差异。

### 2.4 学期课程数：去掉打开菜单/学期弹窗时的同步查库

课表菜单的学期色块与学期滚轮选择器需要「各学期课程数」，旧实现每次打开都同步执行
`executeDb { dao.getAllCourses() }`（主线程等 DB 线程，低端机上会叠加在菜单 inflate 之上）。

现在 `CourseDataManager` 在已存在的 Room Flow 监听里顺带算出 `semesterId → 课程数` 缓存
（同一份全量数据，零额外查询）；所有写操作后先把缓存置空，下一次读取回退到一次查询保证数字准确，
Flow 新值到达再回填。**读取语义与旧实现一致**（永远反映当前数据库内容），只是打开菜单时不再查库。

## 3. 工作流 B：课表渲染与每秒热路径

### 3.1 `TimeTableManager`：时间表解析缓存

- `getTimeSlots()` / `getMaxNodes()` 改为内存缓存（`@Volatile`，双重检查）；
- `saveTimeSlots / setMaxNodes / resetToDefault` 在同一把锁内**先更新 SharedPreferences 内存镜像再换缓存**，
  保证保存后所有线程立即看到新值，不存在新旧混搭；
- 返回值语义逐分支保持（顺序、默认 13 节、空/异常回退默认时间表）。

收益：倒计时每秒 **15~40 次 Gson 解析 → 0 次**；周课表每页 bind 与 6 款小组件刷新同样归零。

### 3.2 倒计时：只在可见时算，且把一天内不变的部分缓存起来

- `onStart` 启动、`onStop` 停止（视图销毁时 `removeCallbacks`），页面不可见完全不跑；
- 「今日课程 + 起止分钟」按 `(课程列表引用, 当前周, 自然日, 时间表引用)` 缓存：
  跨天/跨周/改时间表/课程数据变化才重算，其余每秒只做 n 次 int 比较；
- 文本与可见性做同值短路，避免每秒 `setText` 触发重绘。

等价性：旧实现两遍 `find`（当前课/下一课）与新的单次顺序扫描结果一致（`when` 分支只用到其中之一）；
缓存键包含所有会影响结果的输入，用户改时间表后**返回课表页第一秒**即重算。

### 3.3 周课表：按周预计算 + 去掉每 bind 的重复动作

- 新增按周缓存：`filter(本周有课 + 有固定时间) → groupBy(星期, 开始节, 结束节) → 组内按优先级排序`，
  `updateData()` 时整体失效；组序与旧 `groupBy` 插入序一致（决定卡片叠放），组内排序实现只从
  ViewHolder 提到文件级共用（同一份 `courseSortKey`）。
- 网格背景配置并入「时间轴需要重建」的分支：旧实现每次 bind 都重设 `gridColor`（`setter` 无条件
  `invalidate` 整页），现在只在真正需要时配置。
- `Calendar` / `TypedValue` / 当日列淡底 `GradientDrawable` 复用；底部留白高度未变时不 `requestLayout`；
  深色模式与透明度提到循环外；卡片文字用 `buildString`（输出与 `joinToString` 相同）。

### 3.4 总课表

- 切换「周课表 ⇄ 总课表」时，课程列表引用未变则复用上次归并结果（`CourseOverviewGroup.build` 是纯函数）。
- `CourseOverviewAdapter` 头像/类型标签两个 `GradientDrawable` 改为 ViewHolder 复用，只改颜色。

### 3.5 自定义 View 审计

- `GridBackgroundView`：网格色透明时 `onDraw` 已直接 return（0 绘制）；setter 加同值短路。
- `VerticalScrollView` / `PillBottomNavView`：逐行审计后无每帧浪费，**未改**。

## 4. 工作流 C：桌面小组件与后台刷新链

### 4.1 进程内「桌面实例」缓存

新增 `widget/WidgetPresence.kt`：`HashMap<Class<*>, IntArray>`，由 `onUpdate`（完整 id 列表替换）、
`onDeleted`、`onDisabled`、`onEnabled` 维护；首次（进程刚启动）才查一次 `AppWidgetManager`，
查询异常不写缓存、下次重试。对外两个契约：

- `MinimalWidgetProvider.isPlaced(context)`：是否有「下课倒计时」实例；
- `ScheduleWidgetUpdateService.hasAnyWidget(context)`：6 款组件是否有任一实例。

### 4.2 每秒 tick：内容签名门控

把「计算要显示的内容」与「构建/提交 RemoteViews」拆开：

1. 先算内容快照 + 签名（状态、课名/教室/教师、倒计时文本、目标分钟、Chronometer 格式、自然日、深浅色模式等）；
2. 与该 widgetId 上次成功提交的签名比较：**相同直接返回**，不 `new RemoteViews`、不 IPC；
3. 变化时才批量 `updateAppWidget`；系统/闹钟驱动的 `onUpdate`、`onEnabled`、改时间/跨天走
   `triggerUpdateNow` 强制提交，原有刷新时机不变。

视觉等价：RemoteViews 幂等，跳过提交等价于系统保留上次完全相同的内容；倒计时秒数由宿主
`Chronometer` 自走秒，跳过提交不影响逐秒跳字。额外加「倒计时分钟桶」把 NTP 校时后的基准漂移限制在 1 分钟内。

**签名比对本身也算内容**，所以内容计算同样做了缓存：`MinimalWidgetProvider` 把
「今日课程（按开始分钟升序）+ 每门课起止分钟」按 `(课程列表引用, 星期, 周次, 时间表引用)` 缓存，
稳定态每秒只剩 n 次 int 比较；旧路径每秒都 filter 全部课程 + `sortedBy`（比较器里逐个按节次
查时间表并 `split(":")` 解析 HH:mm）。跨天/跨周/改时间表/课程数据变化时缓存自动失效。

### 4.3 刷新链瘦身

- 5 条每组件 15 分钟 `setInexactRepeating` → **1 条共用**（requestCode 沿用 10003，覆盖旧闹钟；
  旧 10004/10009/10010/10015 用 `FLAG_NO_CREATE` 探测并清理一次）；
- 30 分钟精确链 / 午夜闹钟 / 开机链：`hasAnyWidget` 为假时不再排程；残留链醒来一次即自愈取消；
- 课程结束瞬间多个 provider 的同内容重复刷新加 2 秒去重窗口（保留各自独立兜底链）；
- RemoteViews/PendingIntent 进程内复用；近日课程两个 ListView 的数据重载改为按内容签名去重；
- 各闹钟接收器在对应组件不存在时直接返回。

### 4.4 节次 → 分钟换算缓存

`CourseTimeUtils.getStartMinutes/getEndMinutes` 被 6 款小组件的刷新路径调用（倒计时组件在每秒
内容计算里还会遍历今日课程的所有起止分钟）。原实现每次换算都要 `getTimeSlots().find{...}` 扫描
时间表并 `split(":")` 解析 HH:mm；现在按「时间表快照引用」缓存 `node → 分钟` 映射，
保存时间表后自动失效。语义逐条对齐（重复 node 取第一条、非法 HH:mm 走原估算兜底、异常兜底）。

稳定性：本次改动后手工覆盖「冷启动 → 周课表 → 总课表 → 返回周课表」路径，`logcat -b crash`
中**没有任何 `com.cherry.wakeupschedule` 的 FATAL EXCEPTION**（账本里只有模拟器自身
`system_server`/GMS 因软件模拟过慢被杀后各应用的 `DeadSystemException`）。
`monkey` 随机压测在 TCG 模拟器上会在第 3 个事件前压死系统服务，**不能作为 App 稳定性判据**，
因此改用真实操作路径 + 日志核对。

### 5.3 未被改变的 UI（结构性保证）

所有 UI 定义资源零改动；渲染代码只改了"如何得到相同的值"（缓存/复用/短路），
每个改动点都用「输出与旧实现逐字段一致」的方式论证（见 `develop/perf/*.md`）。

## 6. 未实施的可选项与原因

| 可选项 | 预期收益 | 不做的原因 |
| --- | --- | --- |
| 去掉 Activity 根层渐变（Fragment 自己已铺满，根层渐变被完全遮住） | 省一层全屏填充（低端 GPU 约 1~2ms/帧） | 冷启动首帧时 Fragment 视图可能尚未 attach，会闪一下窗口底色——属于可观察视觉变化，按硬约束放弃 |
| 课表菜单弹层预加载（AsyncLayoutInflater 预热） | 菜单首次打开更快 | 菜单内含动态状态与大量监听器，复用/预加载的等价性无法在无真机条件下证明，风险 > 收益 |
| 课程卡片 View 复用池 | 翻周重绑时减少 View 创建 | 需维护 z 序/角标/点击闭包，视觉与交互回归风险高 |
| 时间轴改自绘 / 合并课程卡 View 层级 | 减少图层与 TextView 数 | 直接改变渲染结果，违反"零视觉变化" |
| Baseline Profile / 启动编译优化 | 冷启动再提速 | 需要真机 profiling 生成，本机无 KVM 无法生成可信 profile；手写 profile 可能负优化 |
| Room 增加索引（semester_id） | 查询更快 | 课程表数据量小（百级），收益可忽略，却要新增迁移版本与 schema 快照 |
| 其他 5 款小组件加签名门控 | <1% | 它们是分钟级/事件级刷新，收益可忽略，diff 越大回归面越大 |

## 7. 剩余待办 / 回归自测清单

> 本轮已在无 KVM 的 Android 15 模拟器上完成：周课表 / 总课表的「改动前 vs 改动后」实拍像素对比
> （对齐系统栏差异后 **0 像素超过阈值**）、小组件刷新频率 A/B、闹钟合并验证、冷启动主线程阻塞验证、
> 主要路径无崩溃。**下列项目需要在真机（尤其低端机）上做最终确认**，属环境限制而非代码缺口。

1. **其余界面像素复核**：课表菜单 / 工具 / 我的 / 深色模式。这三处渲染代码本次零改动，
   属结构性等价；受无 KVM 模拟器的 GPU 颜色缓冲损坏限制未完成实拍。
2. **小组件重点回归**（改动最结构性）：
   - 只放 1 款 / 同时放多款组件时，15 分钟兜底刷新仍工作（`dumpsys alarm` 应只见 1 条共用周期闹钟）；
   - 添加/移除组件后 `isPlaced/hasAnyWidget` 与实际一致；
   - 升级覆盖安装后旧闹钟（10004/10009/10010/10015）消失；
   - 「下课倒计时」在上下课、整点、跨天、改系统时间/时区时仍准时切换。
3. **冷启动路径**：Splash → 首帧课表数据完整；杀进程后从「最近任务」直入 GPA/成绩/考试/我的/绑定页数据正确；
   桌面小组件冷启动拉起进程时课程/学期非空。
4. **课表交互**：翻周/滑周、重叠角标与弹窗顺序、今日高亮/当日淡底、底部留白、格子高度/边框/教室教师开关、
   总课表筛选。
5. **倒计时**：退后台回前台立即正确、切 tab 往返、「今日课程已结束」、无课隐藏。
6. **时间表编辑**：改时间/增删/重置后返回课表倒计时立即正确，重启后自定义时间表生效。
7. **低端真机帧率/内存**：用 `adb shell dumpsys gfxinfo <pkg> framestats` 与 Android Studio Profiler
   在目标机型上做一次冷启动与翻周采样，确认无掉帧热点残留。

## 8. 维护约定（改这些代码时注意）

- 新增"读取学期/课程/账号缓存"的入口：若可能不经 `MainActivity`/`SplashActivity` 启动，必须保证
  读取发生在 `AppInitializer.awaitReady()` 之后（或调用上述三扇门），否则会读到未就绪缓存。
- `TimeTableManager` 的缓存与保存必须成对更新（同一把锁内先 prefs 后缓存）；不要绕过 `saveTimeSlots` 直接写 prefs。
- `WeekPagerAdapter` 的按周缓存只在 `updateData()` 失效；如果以后新增"原地修改课程列表"的写路径，
  必须改成整体替换或显式失效，否则会渲染旧数据。
- 倒计时缓存键包含 `(allCourses 引用, 周, 天, timeSlots 引用)`；新增影响倒计时的设置项时要把设置加进键或显式失效。
- 小组件：任何新增刷新时机必须保证"每实例签名变化时会提交"；`WidgetPresence` 的缓存只能由
  provider 生命周期回调维护，不要从业务代码直接改。
