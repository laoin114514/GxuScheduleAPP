# 测试版（Beta）构建与发布

> 面向开发者的操作手册：如何在本地打 tag、构建与正式版并存的测试包，并直传更新服务端的测试渠道。
> 相关文件：`scripts/beta_release.py`、`app/build.gradle` 的 `beta` build type、`.github/workflows/release.yml`。

## 0. 一句话说明

正式版走 GitHub Actions（推 `vX.Y.Z` tag → `assembleRelease` → 传 `schedule` 渠道）；
**测试版完全在本地完成**（打 `vX.Y.ZbetaN` tag → 本地脚本 → 独立签名/包名/名称 → 传 `schedule-beta` 渠道），
两条链路互不影响：正式用户永远不会收到测试包。

## 1. 渠道对照

| 项 | 正式版（stable） | 测试版（beta） |
|---|---|---|
| 触发 | 推 `vX.Y.Z` tag，GitHub Actions | 本地跑 `scripts/beta_release.py` |
| 构建类型 | `release` | `beta`（`initWith release`，同样跑 R8/资源压缩） |
| 包名 | `com.cherry.wakeupschedule` | `com.cherry.wakeupschedule.beta` |
| App 显示名 | 西大课栈 | 西大课栈 Beta |
| 签名 | 正式 keystore（仅存 CI secrets） | `wakeup-schedule-beta-key.jks`（本地生成） |
| 更新渠道 appKey | `schedule` | `schedule-beta` |
| versionName | `0.5.12` | `0.5.12-beta.1` |
| versionCode | `base*10` = 5120 | `base*10 + N` = 5121 |
| 发布位置 | GitHub Releases + 更新服务 | 仅更新服务（可选推 tag / 不建 GitHub Release） |
| 与正式版关系 | — | 同机共存、数据独立、互不覆盖 |

`base = MAJOR*10000 + MINOR*100 + PATCH`（如 `0.5.12` → `512`），与 CI 的版本号口径完全一致。

## 2. 一次性准备

### 2.1 生成测试版签名与本地配置

```bash
python3 scripts/beta_release.py --init-signing
```

会做三件事：

1. 生成 `wakeup-schedule-beta-key.jks`（PKCS12 / RSA 2048 / 10000 天，随机密码）；
2. 生成 `.beta-release.env`（权限 600，已被 `.gitignore` 忽略）；
3. 打印备份提醒。

> **必须离线备份 jks 与密码**。证书丢失后，测试者将无法覆盖安装新 beta（签名不一致只能卸载重装）。

如果已有签名文件，也可以手动复制 `.beta-release.env.example` 为 `.beta-release.env` 并填写。

### 2.2 上传 key 从哪里来（当前部署无需改后端）

当前部署方式下，更新服务（`schedule-server` 容器）与构建机是同一台机器，正式上传 key
本来就在 `GxuScheduleWebsite/.env` 的 `UPLOAD_API_KEY` 里。因此：

- **后端不需要任何改动**：测试版渠道隔离靠 appKey（`schedule-beta`）实现，
  现有服务端天然支持任意合法 appKey，首次上传会自动建 App 记录；
- `.beta-release.env` 里把 `UPDATE_API_KEY` 留空、配置
  `SERVER_ENV_FILE=GxuScheduleWebsite/.env`，脚本会自动读取该文件的 `UPLOAD_API_KEY`，
  不需要把密钥复制到第二处；
- 更新服务不在本机时：删掉 `SERVER_ENV_FILE`，直接填 `UPDATE_API_KEY=<服务端上传 key>`。

> 小技巧（单机部署）：本机直连容器更快更稳，可把 `UPDATE_BASE_URL` 改成
> `http://127.0.0.1:8080`（容器监听在根路径，**不要**加 `/schedule` 前缀）。
> App 里的更新地址仍是 `https://easo.laoin.work/schedule`，不受影响。

> 可选加固（**当前已实现但不合并、不部署**）：如果以后更新服务迁到远端 VPS、而构建机仍在本地，
> 建议启用「beta 专用上传 key」——服务端加可选配置 `UPLOAD_API_KEY_BETA`，
> 该 key 只能上传 appKey 以 `-beta` 结尾的渠道，本机即使只有这把 key 也无法伪造正式版。
> 代码保留在 `GxuScheduleWebsite` 仓库的 `feat/beta-scoped-upload-key` 分支，
> 迁移时 merge 分支 + 服务端 `.env` 加一行 `UPLOAD_API_KEY_BETA=<openssl rand -hex 32>` 并重启即可。
>
> 为什么当前不做：更新服务与密钥本来就在同一台构建机上（`GxuScheduleWebsite/.env` 可直接读到
> 正式 key），此时再区分一把 beta key 并不能提升实际安全性，只会增加配置与部署复杂度。

## 3. 版本号与 tag 规范

| tag | versionName | versionCode | 说明 |
|---|---|---|---|
| `v0.5.12beta` | `0.5.12-beta.1` | 5121 | 等价于 beta1 |
| `v0.5.12beta2` | `0.5.12-beta.2` | 5122 | 同一版本第 2 个测试包 |
| `v0.5.13beta1` | `0.5.13-beta.1` | 5131 | 升 patch 后的第一个测试包 |

规则：

- 序号范围 `1..9`，同一 base 超过 9 个测试包请提升 patch；
- 测试渠道 versionCode 必须严格递增（服务端拒绝降级/同号不同内容）；
- 同一版本的测试包内容有变，请 `beta2`、`beta3` 递增，不要复用序号；
- 正式版 `v0.5.12` 与测试版 `v0.5.12beta1` 的 versionCode 分别是 5120 / 5121，属于不同渠道，不冲突。

推荐全程使用 annotated tag（注释会成为默认更新说明，与正式发版约定一致）：

```bash
git tag -a v0.5.12beta1 -m "修复课表刷新闪退" -m "- 修复 xxx
- 优化 yyy"
```

## 4. 发版流程

```bash
# 1) 确认工作区干净（脚本会校验；tag 必须正好指向 HEAD）
git status

# 2) 打 tag
git tag -a v0.5.12beta1 -m "标题" -m "更新说明"

# 3) 先干跑看看计划（可选）
python3 scripts/beta_release.py --dry-run

# 4) 完整流程：构建 → 校验 → 上传
python3 scripts/beta_release.py
```

脚本按顺序执行：

1. 解析 tag → 版本号 / versionCode；校验 tag 指向 HEAD、工作区干净、同 base 没有更高序号 tag；
2. 查询更新服务：测试渠道最新版本必须低于本次版本；基线低于正式版会给出 warning；
3. `./gradlew :app:assembleBeta -PappVersionCode=... -PappVersionName=... -PbetaIndex=...`
   （签名密码通过 `ORG_GRADLE_PROJECT_BETA_*` 环境变量传入，不进入命令行/日志）；
4. 用 `aapt` 校验包名 / versionCode / versionName / 显示名，用 `apksigner` 校验签名，算 sha256；
5. `curl` 上传 `schedule-beta` 渠道（带重试），校验响应；
6. 上传后复检渠道版本，并断言 **正式渠道 latest 未发生变化**（防止误传）；
7. 写本地发版记录 `build/beta-releases/<tag>.json`，打印测试者安装说明。

常用参数：

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只预检、打印计划 |
| `--skip-upload` | 只构建 + 校验 + 记录 |
| `--skip-build --apk <path>` | 复用已有 APK 上传 |
| `--notes "..."` / `--notes-file <path>` | 指定更新说明（默认用 tag 注释 → 上一个 tag 以来的提交） |
| `--install` | 构建后 `adb install -r -d` 到已连接设备 |
| `--push-tag` | 上传成功后推送 tag（CI 会跳过 beta tag） |
| `--offline` | 跳过服务端预检（无网络时只构建） |
| `--env-file <path>` | 指定本地配置文件 |
| `--allow-dirty` | 允许工作区脏（仅调试用，产物不代表 tag 内容） |

## 5. 测试者安装与更新

给测试者的话：

1. 直接安装「西大课栈 Beta」。与正式版是两个独立 App，可同机共存，测试数据不会影响正式版；
2. 首次安装需要允许「安装未知来源应用」（测试版包名独立，需要单独授权）；
3. 安装后每次启动 App 都会检查测试渠道更新（正式版是每日一次），有新版直接点更新覆盖安装；
4. 想回正式版：卸载 Beta，重新安装正式版即可（正式版数据一直不受影响）。

## 6. 失败码与排查

| 现象 / 退出码 | 原因 | 处理 |
|---|---|---|
| `401 invalid api key` | 上传 key 错误 / `SERVER_ENV_FILE` 指向错误 / 服务端改 .env 后未重启 | 核对 `GxuScheduleWebsite/.env` 的 `UPLOAD_API_KEY`；改完 `.env` 需 `docker compose up -d` 重启 |
| `403 beta 上传密钥仅允许...` | beta key 上传了非 `-beta` 渠道 | 脚本已固定 appKey，检查是否手工改过 |
| `409 versionCode 已存在且文件内容不同` | 同序号重发不同内容 | 换 `beta2`、`beta3` |
| `409 低于当前最新` | 版本号倒退 | 提升版本号 / beta 序号 |
| 退出码 3 | Gradle 构建失败 | 看上方构建日志；先跑通 `./gradlew :app:assembleBeta ...` |
| 退出码 4 | APK 校验失败 | 检查 beta build type 配置、签名密码；`local.properties` 的 sdk.dir 是否正确 |
| `tag 不在当前 HEAD 上` | tag 之后又提交了代码 | 重新在 HEAD 打 tag |
| `工作区有未提交的改动` | 产物与 tag 内容不一致 | 先提交（调试可 `--allow-dirty`） |
| 上传超时 | 网络不稳 | 重跑即可；服务端按 `(appKey, versionCode, sha256)` 幂等 |

## 7. 正式版发布链路（不受影响）

- 推 `vX.Y.Z` tag → release.yml 构建正式包、上传 `schedule` 渠道、创建 GitHub Release；
- **beta tag 会被 release.yml 直接跳过**（job 级 `if` + 兜底校验双重拦截），不会产出正式包；
- 因此 beta tag 可以只留在本地，也可以 `--push-tag` 推到远端留档，都不会触发正式发版。

## 8. 为什么测试版要独立包名/签名

- 独立包名：与正式版同机共存；测试版的崩溃、清数据、卸载都不会影响正式版；
- 独立签名：正式签名只存在 CI，本地不可能拿到，测试版必须能独立构建与安装；
- 独立 appKey：正式用户永远查不到 beta，测试者也不会被正式版的更新节奏打扰；
- 独立 keystore 的风险是「丢失后无法覆盖安装」，所以必须备份（见 §2.1）。
