# 测试版（Beta）构建与发布

> 面向开发者的操作手册：如何在本地打 tag、构建与正式版并存的测试包，并直传更新服务端的测试渠道。
> 相关文件：`scripts/beta_release.py`、`app/build.gradle` 的 `beta` build type、`.github/workflows/release.yml`。

## 0. 一句话说明

正式版走 GitHub Actions（推 `vX.Y.Z` tag → `assembleRelease` → 用 `schedule` 渠道专属 key 上传
`schedule` 渠道）；**测试版完全在本地完成**（打 `vX.Y.ZbetaN` tag → 本地脚本 → 独立签名/包名/名称 →
用 `schedule-beta` 渠道专属 key 上传 `schedule-beta` 渠道），两条链路互不影响：正式用户永远不会收到测试包。
每个渠道一把独立上传 key（`gxu_live_...`，服务端只存 SHA-256），由管理面 admin API 签发。

## 1. 渠道对照

| 项 | 正式版（stable） | 测试版（beta） |
|---|---|---|
| 触发 | 推 `vX.Y.Z` tag，GitHub Actions | 本地跑 `scripts/beta_release.py` |
| 构建类型 | `release` | `beta`（`initWith release`，同样跑 R8/资源压缩） |
| 包名 | `com.cherry.wakeupschedule` | `com.cherry.wakeupschedule.beta` |
| App 显示名 | 西大课栈 | 西大课栈 Beta |
| 签名 | 正式 keystore（仅存 CI secrets） | `wakeup-schedule-beta-key.jks`（本地生成） |
| 更新渠道 appKey | `schedule` | `schedule-beta` |
| versionName | `0.5.12` | `0.5.12-beta.1` |
| versionCode | `base*10` = 5120 | `base*10 + N` = 5121 |
| 发布位置 | GitHub Releases + 更新服务 | 仅更新服务（可选推 tag / 不建 GitHub Release） |
| 与正式版关系 | — | 同机共存、数据独立、互不覆盖 |

`base = MAJOR*10000 + MINOR*100 + PATCH`（如 `0.5.12` → `512`），与 CI 的版本号口径完全一致。

## 2. 一次性准备

### 2.1 生成测试版签名与本地配置

```bash
python3 scripts/beta_release.py --init-signing
```

会做三件事：

1. 生成 `wakeup-schedule-beta-key.jks`（PKCS12 / RSA 2048 / 10000 天，随机密码）；
2. 生成 `.beta-release.env`（权限 600，已被 `.gitignore` 忽略），其中 `UPDATE_API_KEY` 留空；
3. 打印备份提醒与管理面签发上传 key 的提示（key 本身见 §2.2）。

> **必须离线备份 jks 与密码**。证书丢失后，测试者将无法覆盖安装新 beta（签名不一致只能卸载重装）。

如果已有签名文件，也可以手动复制 `.beta-release.env.example` 为 `.beta-release.env` 并填写
（其中 `UPDATE_API_KEY` 填 §2.2 签发的 beta 渠道 key）。

### 2.2 上传 key 从哪里来（用 admin API 签发 beta 渠道专属 key）

新方案下**每个 app（渠道）有自己的 upload key**，格式 `gxu_live_<keyId8>_<43字符>`；服务端只存
SHA-256，按 key 反查 app，明文只在 admin API 签发/轮换时返回一次。测试版必须用 `schedule-beta`
渠道的 key（拿 `schedule` 渠道的 key 上传会被服务端以 `APP_KEY_MISMATCH` 拒绝）。

**管理密钥 `ADMIN_API_KEY` 只放管理员本机**（它等价于服务端 `.env` 里的 `ADMIN_API_KEYS` 之一），
绝不写进 `.beta-release.env`、不进 CI、不进 shell 历史；需要时临时 `read -s` 或 `export`。
下面命令假设当前 shell 已 `export UPDATE_BASE_URL=...`（与 `.beta-release.env` 一致）和
`export ADMIN_API_KEY=...`；也可以 `set -a; . ./.beta-release.env; set +a` 载入 base URL。

1. 确认更新服务已切到新版本且 `schedule-beta` app 存在（迁移时会有；全新库先创建）。
   首次创建 app 时可顺手签发第一把 key（明文只在这一个响应里）：

   ```bash
   # 409 APP_EXISTS 说明 app 已存在，直接做第 2 步
   curl -sS -X POST "${UPDATE_BASE_URL}/api/v1/admin/apps" \
     -H "Authorization: Bearer ${ADMIN_API_KEY}" \
     -H "Content-Type: application/json" \
     -d '{"appKey":"schedule-beta","name":"西大课栈 Beta","issueKey":true,"label":"local-beta"}'
   ```

2. 给 `schedule-beta` 签发 beta 渠道 key：

   ```bash
   curl -sS -X POST "${UPDATE_BASE_URL}/api/v1/admin/apps/schedule-beta/keys" \
     -H "Authorization: Bearer ${ADMIN_API_KEY}" \
     -H "Content-Type: application/json" \
     -d '{"label":"local-beta"}'
   # → {"code":0,...,"data":{"keyId":"...","plaintext":"gxu_live_...","..."}}
   #   data.plaintext 就是唯一一次能看到的明文 key
   ```

3. 把 `data.plaintext` 填进 `.beta-release.env` 的 `UPDATE_API_KEY`（文件已被 `.gitignore` 忽略，
   权限建议 600）。只有这一步需要把 key 落到本地文件；脚本不再从服务端 `.env` 读任何 key。

**轮换**：怀疑泄露或定期轮换时，用 `POST /api/v1/admin/keys/{keyId}/rotate` 签发新 key（旧 key
进入 `retiring` 宽限期，默认 24 小时，期间仍可上传）；把新明文更新到 `.beta-release.env` 后，
旧 key 到期自动失效，也可以立即 `POST /api/v1/admin/keys/{keyId}/revoke` 吊销。
正式渠道（`schedule`）的 key 同理：在 GitHub 仓库 Settings → Secrets 里换成 `SCHEDULE_UPLOAD_KEY`。

> 单机部署小技巧：本机直连容器更快更稳，可把 `UPDATE_BASE_URL` 改成
> `http://127.0.0.1:8080`（容器监听在根路径，**不要**加 `/schedule` 前缀）。
> App 里的更新地址仍是 `https://easo.laoin.work/schedule`，不受影响。
>
> admin API 也可以走本机地址（同样不要加 `/schedule`）；这是唯一推荐使用管理密钥的场景。
> 详见 [`GxuScheduleWebsite/docs/per-app-upload-keys.md`](../GxuScheduleWebsite/docs/per-app-upload-keys.md)。

## 3. 版本号与 tag 规范

| tag | versionName | versionCode | 说明 |
|---|---|---|---|
| `v0.5.12beta` | `0.5.12-beta.1` | 5121 | 等价于 beta1 |
| `v0.5.12beta2` | `0.5.12-beta.2` | 5122 | 同一版本第 2 个测试包 |
| `v0.5.13beta1` | `0.5.13-beta.1` | 5131 | 升 patch 后的第一个测试包 |

规则：

- 序号范围 `1..9`，同一 base 超过 9 个测试包请提升 patch；
- 测试渠道 versionCode 必须严格递增（服务端拒绝降级/同号不同内容）；
- 同一版本的测试包内容有变，请 `beta2`、`beta3` 递增，不要复用序号；
- 正式版 `v0.5.12` 与测试版 `v0.5.12beta1` 的 versionCode 分别是 5120 / 5121，属于不同渠道，不冲突。

推荐全程使用 annotated tag（注释会成为默认更新说明，与正式发版约定一致）：

```bash
git tag -a v0.5.12beta1 -m "修复课表刷新闪退" -m "- 修复 xxx
- 优化 yyy"
```

## 4. 发版流程

```bash
# 1) 确认工作区干净（脚本会校验；tag 必须正好指向 HEAD）
git status

# 2) 打 tag
git tag -a v0.5.12beta1 -m "标题" -m "更新说明"

# 3) 先干跑看看计划（可选）
python3 scripts/beta_release.py --dry-run

# 4) 完整流程：构建 → 校验 → 上传
python3 scripts/beta_release.py
```

脚本按顺序执行：

1. 解析 tag → 版本号 / versionCode；校验 tag 指向 HEAD、工作区干净、同 base 没有更高序号 tag；
2. 查询更新服务：测试渠道最新版本必须低于本次版本；基线低于正式版会给出 warning；
3. `./gradlew :app:assembleBeta -PappVersionCode=... -PappVersionName=... -PbetaIndex=...`
   （签名密码通过 `ORG_GRADLE_PROJECT_BETA_*` 环境变量传入，不进入命令行/日志）；
4. 用 `aapt` 校验包名 / versionCode / versionName / 显示名，用 `apksigner` 校验签名，算 sha256；
5. `curl` 上传 `schedule-beta` 渠道（带重试），校验响应；
6. 上传后复检渠道版本，并断言 **正式渠道 latest 未发生变化**（防止误传）；
7. 写本地发版记录 `build/beta-releases/<tag>.json`，打印测试者安装说明。

常用参数：

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只预检、打印计划 |
| `--skip-upload` | 只构建 + 校验 + 记录 |
| `--skip-build --apk <path>` | 复用已有 APK 上传 |
| `--notes "..."` / `--notes-file <path>` | 指定更新说明（默认用 tag 注释 → 上一个 tag 以来的提交） |
| `--install` | 构建后 `adb install -r -d` 到已连接设备 |
| `--push-tag` | 上传成功后推送 tag（CI 会跳过 beta tag） |
| `--offline` | 跳过服务端预检（无网络时只构建） |
| `--env-file <path>` | 指定本地配置文件 |
| `--allow-dirty` | 允许工作区脏（仅调试用，产物不代表 tag 内容） |

## 5. 测试者安装与更新

给测试者的话：

1. 直接安装「西大课栈 Beta」。与正式版是两个独立 App，可同机共存，测试数据不会影响正式版；
2. 首次安装需要允许「安装未知来源应用」（测试版包名独立，需要单独授权）；
3. 安装后每次启动 App 都会检查测试渠道更新（正式版是每日一次），有新版直接点更新覆盖安装；
4. 想回正式版：卸载 Beta，重新安装正式版即可（正式版数据一直不受影响）。

## 6. 失败码与排查

上传接口的失败响应格式统一为 `{"code":<HTTP 状态码>,"errorCode":"<稳定错误码>","message":"中文提示"}`。
脚本会优先解析 `errorCode` 并打印中文可操作提示（原始 JSON 也会输出），退出码仍沿用
`3=构建 / 4=校验 / 5=上传 / 2=用法`。

| errorCode | HTTP | 原因 | 处理 |
|---|---|---|---|
| `INVALID_API_KEY` | 401 | key 格式不对 / 不存在 / 已被吊销 / 已过期（如 retiring 宽限期结束） | 用 admin API 重新签发或轮换 `schedule-beta` key，把新明文更新到 `.beta-release.env` |
| `APP_NOT_FOUND` | 403（上传） | 上传时的 appKey 在服务端不存在（不再自动建 app；专属 key 场景不会出现） | 用 admin API 创建该渠道并签发专属 key |
| `APP_DISABLED` | 403 | 该渠道已被管理员停用 | 让管理员 `PATCH /apps/{appKey}` 把 `status` 改回 `1` |
| `APP_KEY_MISMATCH` | 403 | 用的 key 属于别的渠道（常见：拿了正式渠道 `schedule` 的 key） | 换成 `schedule-beta` 渠道的 key |
| `INVALID_PARAM` | 400 | appKey / versionCode / versionName / 文件名等不合法 | 核对 tag 格式与脚本参数；versionCode 需在 1..2100000000，文件名只用 `[A-Za-z0-9._-]` |
| `FILE_TOO_LARGE` | 413 | APK 超过 `MAX_UPLOAD_MB`（app 可单独收紧） | 让管理员调大限额，或确认没传错文件 |
| `VERSION_CONFLICT` | 409 | 同 versionCode 已存在且文件内容不同 | 换 `beta2`、`beta3`（同一 APK 重传是幂等的） |
| `DOWNGRADE_REJECTED` | 409 | 本次 versionCode 低于该渠道最新版 | 提升版本号 / beta 序号 |
| `UPLOAD_QUOTA_EXCEEDED` | 429 | 该 app 当日新增 release 次数达上限（`DEFAULT_DAILY_UPLOAD_LIMIT`，默认 20） | 次日再试，或让管理员调大该 app 的每日上限 |
| `RATE_LIMITED` | 429 | 单 key 上传过于频繁（`UPLOAD_RATE_RPS` / `UPLOAD_RATE_BURST`） | 等几秒重跑；curl 已有重试 |
| 响应不是 JSON / 空 | — | 打到了静态托管或反向代理错误页（地址写错、nginx 未反代 `/api`） | 核对 `UPDATE_BASE_URL` 是否指向后端；本机可用 `http://127.0.0.1:8080` |
| 退出码 3 | — | Gradle 构建失败 | 看上方构建日志；先跑通 `./gradlew :app:assembleBeta ...` |
| 退出码 4 | — | APK 校验失败 | 检查 beta build type 配置、签名密码；`local.properties` 的 sdk.dir 是否正确 |
| 退出码 5 | — | 上传阶段失败（见上方 errorCode 提示） | 按 `errorCode` 对应行处理 |
| `tag 不在当前 HEAD 上` | — | tag 之后又提交了代码 | 重新在 HEAD 打 tag |
| `工作区有未提交的改动` | — | 产物与 tag 内容不一致 | 先提交（调试可 `--allow-dirty`） |
| 上传超时 | — | 网络不稳 | 重跑即可；服务端按 `(appKey, versionCode, sha256)` 幂等 |

## 7. 正式版发布链路

- 推 `vX.Y.Z` tag → release.yml 构建正式包，用 GitHub Actions secret `SCHEDULE_UPLOAD_KEY`
  （`schedule` 渠道专属上传 key）上传到 `schedule` 渠道，再创建 GitHub Release；
- **beta tag 会被 release.yml 直接跳过**（job 级 `if` + 兜底校验双重拦截），不会产出正式包；
- 因此 beta tag 可以只留在本地，也可以 `--push-tag` 推到远端留档，都不会触发正式发版。

> admin API 用法、key 轮换/吊销与排障见
> [`GxuScheduleWebsite/README.md`](../GxuScheduleWebsite/README.md) 与
> [`GxuScheduleWebsite/docs/per-app-upload-keys.md`](../GxuScheduleWebsite/docs/per-app-upload-keys.md)。

## 8. 为什么测试版要独立包名/签名

- 独立包名：与正式版同机共存；测试版的崩溃、清数据、卸载都不会影响正式版；
- 独立签名：正式签名只存在 CI，本地不可能拿到，测试版必须能独立构建与安装；
- 独立 appKey：正式用户永远查不到 beta，测试者也不会被正式版的更新节奏打扰；
- 独立 keystore 的风险是「丢失后无法覆盖安装」，所以必须备份（见 §2.1）。
