# 登录态与重登录机制改造（实现说明）

> 背景实测：[docs/登录状态失效规律实测.md](登录状态失效规律实测.md)（20 后端节点、route 粘性路由、TTL 分档、同节点互踢等规律）。
> 真实账号 E2E 验证证据：`develop/session-expiry/state/impl_verify/results.md`（gitignored，A 部分 Java 客户端级 + B 部分模拟器 App 级，全部 PASS）。
> 本文记录「改了什么、为什么这么改、怎么验证、还有哪些限制」。
>
> 2026-11-03 优化版（在首版基础上追加）：① 会话自动恢复过程对用户可见（"正在恢复/已恢复/被踢恢复"提示）；
> ② 运行时学到的异常节点 7 天后自动失效（避免误标永久化）；③ 按节点学习 TTL 上界，动态收紧前台预热阈值。

## 0. TL;DR

| 问题（改造前） | 改造后 |
| --- | --- |
| 被 route 钉死在异常短 TTL 节点（实测 App 曾钉在 `210.36.22.60`，TTL ≈80–90s）后**永远逃不出去** | 每次完整重登录前 `clearBrowserIdentity()` 清掉 JSESSIONID+route → **随机换节点**；落在已知异常节点再重掷（最多 2 次） |
| 「用到才发现过期」→ 用户点刷新现场等一次完整重登录（≈8s） | App 回到前台时按健康档案判断，**后台预热**：探测/静默重登录提前做掉 |
| 并发双登录（两个页面同时首次请求）→ 同节点互踢 | 所有教务网络/认证操作用 **Mutex 串行化**（单飞），等待方复用结果 |
| 重试分支无兜底 catch → 协程崩溃 | `doWithAuth` 全路径兜底为 `Result.failure`，并区分被踢/过期/网络/凭据/验证码 |
| 被踢与普通过期无法区分，用户只看到「登录已过期」 | Java 客户端识别 `kickout=1` → `KickedOutException`；`probeSession()` 三态 |
| 恢复过程静默，用户只感觉"这次刷新特别慢" | `JwxtAuthManager.notices` 事件流 + `BaseActivity` 收集 → AppToast 提示「正在恢复 / 已恢复 / 被踢恢复」 |
| 会话仍有效时 `updatePassword` 不校验新密码（实测 bug） | 改密前先清会话身份，必须走完整「登录页 → POST」才写入本地密码 |
| cookie 里只有值，没有「上次确认有效的时刻」 | 新增**会话健康档案**（SharedPreferences，不引入 Room 迁移） |
| 所有节点共用同一个预热阈值；误标的坏节点永久拉黑 | 按 route 学习 TTL 上界动态收紧预热阈值（25min → 最短 1min）；运行时坏节点 7 天后自动失效 |

## 1. 设计原则

1. **不做后台常驻保活**（WorkManager 15min 周期对 30min/90s TTL 节点无意义，且耗电）：只在 App 前台做「到期前预热」。
2. **把重登录当作正常路径，让它对用户无感**（提前在后台做），而不是追求「永不过期」；确实要在前台等时，用提示说明"正在恢复"，避免被当成卡死。
3. 节点 TTL 不可写死：默认按「60min 档 × 0.75」并压到 25min（覆盖 30min 档），再**按 route 学习到的 TTL 上界动态收紧**；异常节点主动避开且只避让 7 天。
4. 所有状态变更（清 cookie / 重登录 / 写健康档案）串行化，避免并发登录互相踢。

### 2.2 App 认证层 `JwxtAuthManager.kt`（重写核心逻辑）

- **`authMutex` 串行化**：`ensureClient`、`doWithAuth` 的「取 client + 业务请求 + 恢复 + 重试」、`login` 的凭据验证、`updatePassword`、前台预热全部互斥；并发请求等待并复用同一次登录，杜绝「两个页面各自登录 → 同节点互踢」。
- **`doWithAuth`**：
  1. `ensureClient()`（client 已登录则直接复用；否则 `probeSession` 三态处理）；
  2. 执行业务；成功 → `JwxtSessionHealthStore.markOk(route)`；
  3. `SessionExpiredException` → `recoverSession()`（记录节点健康 + 清身份完整重登录）→ 重试一次；
  4. 任何异常（含重试后再次失效、业务解析异常）都兜底为 `Result.failure`，不再逃出协程崩溃。
- **`fullReloginLocked()`**：`clearBrowserIdentity()`（清全部 cookie 含 `route` + 换 UA）→ `login()` → 记录健康档案；登录落在已知/已学习异常节点则重掷（≤2 次）。
- **`ensureClientLocked()`**：用 `probeSession()` 三态：ALIVE 复用；EXPIRED 记录节点健康后完整重登录；NETWORK_ERROR 抛「网络异常」且**不清凭据**。
- **`noteSessionExpiry()`（节点健康学习）**：会话失效时——
  - 确认有效后 10 分钟内就失效 → 该节点 TTL 异常，记入 `badRoutes`（7 天避让）；
  - 否则把本次存活时长作为该节点 **TTL 上界**（`routeTtlUpperMs`，只保留更小的估计），仅当它比默认 60min 档更短时才记录。被踢/网络失败不算 TTL 证据。
- **`prewarmInBackground(reason)`**：前台预热入口；`needsPrewarm = 已绑定 && now-lastOkAt ≥ 该节点阈值 && 不在凭据/验证码失败冷却期`，其中阈值 = `prewarmAgeFor(routeTtlUpperMs)`：默认 25min，学到更短 TTL 会提前（下限 1min）。ALIVE → 续期（滑动 TTL touch）；EXPIRED → 后台静默重登录；NETWORK_ERROR → 保持现状。
- **登录态事件流**：用户操作触发恢复时发 `RECOVERING_EXPIRED/RECOVERING_KICKED/RECOVERED/RECOVERED_KICKED` 事件（前台预热保持静默），由 `BaseActivity` 收集并用 AppToast 提示。
- **`updatePassword`**：先 `clearBrowserIdentity()` 再 `login()`，确保密码被真正校验（服务端会把"已登录"状态下的登录 POST 直接 302 回 initMenu）。
- **`unbind`**：同时清 cookie 与健康档案。
- **错误分类文案**：被踢 / 过期恢复失败 / 凭据 / 验证码 / 网络分别有可读消息，`CaptchaRequiredException` 仍原样抛给绑定页。
- **失败冷却**：凭据/验证码类失败（`lastFailKind`）30 分钟内不再由预热自动重试，避免本地密码错误时反复失败触发验证码保护/账号锁定。

### 2.3 新增 `JwxtSessionHealthStore.kt`（会话健康档案）

SharedPreferences（`jwxt_session_health`，JSON v2，**不引入 Room 迁移**），AppInitializer 后台初始化。

| 字段 | 含义 |
| --- | --- |
| `route` | 当前会话所在后端节点常量 |
| `lastOkAt` | 最近一次确认会话有效的时刻（预热/快速失效判定的依据，旧 cookie 机制完全没有这个信息） |
| `lastLoginAt` | 最近一次完整登录时刻 |
| `lastFailKind` / `lastFailAt` | 失败分类与时间（冷却、诊断） |
| `badRoutes` | 运行时学习到的异常短 TTL 节点（route → 首次标记时刻；**超过 7 天自动失效**，重复标记不刷新时间） |
| `routeTtlUpperMs` | 各节点已观测到的 TTL 上界（route → 毫秒；只保留更小估计，用于收紧预热阈值；被"实际存活超过上界"推翻时自动清除） |

写入点：登录成功、探测 ALIVE、业务请求成功（`markOk`）；快速失效（`markRouteBad`）；TTL 学习（`markRouteTtlUpper`）；失败（`markFailure`）；解绑（`clear`）。

数据格式兼容：v1 的 `badRoutes` 是纯字符串数组（无时间戳、无法衰减），升级后直接丢弃（内置已知异常节点不受影响）；当前版本写 JSON v2（对象形式）。

### 2.4 新增 `JwxtAuthPolicy.kt`（纯函数策略，可单测）

| 常量 | 值 | 依据 |
| --- | --- | --- |
| `PREWARM_AGE_MS` | 25 分钟（上限） | 正常档最短 30 分钟（`.55`），留 5 分钟余量；多数节点 60 分钟 |
| `MIN_PREWARM_AGE_MS` | 1 分钟（下限） | 学到极短 TTL 时也避免高频探测 |
| `QUICK_EXPIRY_MS` | 10 分钟 | 登录/确认有效后 10min 内失效 → 节点 TTL 异常（正常 ≥30min） |
| `FAIL_COOLDOWN_MS` | 30 分钟 | 凭据/验证码失败后的自动重登冷却 |
| `BAD_ROUTE_TTL_MS` | 7 天 | 运行时学习的坏节点自动失效，避免一次误判永久避开 |
| `MAX_NODE_REROLL` | 2 | 1/20 概率撞异常节点，重掷 2 次后接受 |
| `KNOWN_BAD_ROUTES` | `2a353708a723ad925112de2eb5f2f993`（= `210.36.22.60`，实测 TTL ≈80–90s） | 内置已知异常节点；运行时继续学习 |

策略函数：`prewarmAgeFor(ttlUpperMs)`（动态阈值）、`shouldPrewarm(now, lastOkAt, ttlUpperMs)`、`isNodeSuspicious`、`isLearnedBadRoute`、`shouldAutoReloginAfterFailure`、`isKnownBadRoute`。

### 2.5 挂载点 / 初始化

- `MainActivity.onResume`、`ScheduleFragment.onResume`：调用 `JwxtAuthManager.prewarmInBackground(...)`（阈值节流，重复调用会被健康档案挡住）。
- `BaseActivity`（所有页面基类）：仅在 RESUMED 期间收集 `JwxtAuthManager.notices`，用 AppToast 显示恢复过程提示（避免后台页面重复弹）。
- `AppInitializer.runInit`：新增 `JwxtSessionHealthStore.init(app)`。
- `RoomCookieJar.cookieValue(name)`：只读取 `route`（供健康档案记录/判断）。
- 测试：`app/src/test/.../JwxtAuthPolicyTest.kt`（策略单测 10 个）；`app/src/androidTest/.../JwxtSessionHealthStoreTest.kt`（健康档案仪器化测试 6 个，不联网、不涉及真实账号）。

## 3. 行为对照（改造前后）

| 场景 | 改造前 | 改造后 |
| --- | --- | --- |
| 正常节点闲置 > 60min 后首次操作 | 现场等完整重登录（≈8s，整体 12–13s） | 回前台预热已静默重登（实测 App 冷启动 **9.09s 后台完成**，用户操作时直接可用） |
| App 被钉在 `.60`（80–90s TTL） | 每 90s 失效、重登也回 `.60`，永远逃不掉 | 失效后清身份重登 → 随机节点（实测 `.60 → .219`）；落回已知异常节点会重掷 |
| 多设备同节点互踢 | 静默 ping-pong、轮流掉线 | 清 identity 随机换节点（95% 不再撞），链条断裂；被踢可识别 |
| 两页面并发首次请求 | 可能双登录 → 同节点互踢 | Mutex 单飞，只登录一次（模拟器 B1/B2 双 onResume 验证只有一对日志） |
| 重试后再次失效/解析异常 | 协程崩溃 | `Result.failure` + 可读消息 |
| 改密输错密码 | 显示“密码已更新”，之后永久“登录已过期” | 报错、保留旧密码（先清身份再登录，真正校验） |
| 会话恢复过程 | 静默，用户以为卡死 | 提示「教务登录已过期，正在自动恢复…」→「教务登录已恢复」；被踢时提示「账号在其它设备登录，正在恢复本机登录…」→「如非本人操作，建议修改密码」 |
| 节点 TTL 明显短于常规（如未来出现 15min 档） | 固定 25min 阈值，可能错过 | 失效样本学习到 TTL 上界后阈值自动提前（如 20min → 15min 预热） |
| 误标坏节点 | 永久避开 | 7 天后自动失效，重新参与随机落点 |

### 4.2 真实账号 E2E（首版改造后验证摘要，详见 results.md）

A 部分（Java 客户端级，8 次登录）：
- `probeSession` 三态：ALIVE（~2.4s）/ EXPIRED（logout 后，普通过期非被踢）/ NETWORK_ERROR（关闭端口 26ms）；
- 被踢：A/B 同节点，B 登录后 A 业务请求抛 **`KickedOutException`**（412ms），普通过期对照为 `SessionExpiredException`；
- 清身份换节点：cookie 归零（0 个）→ 重登 8.28s → route `.49→.218` → 业务成功 ALIVE；
- 完整登录耗时基线 **7.15–8.71s**（含 1.2s/请求限流），probe ~2.4s，业务 ~1.45s。

B 部分（模拟器 App 级，保留旧现场）：
- B1 冷启动预热：旧 11/2 失效会话 + route 钉在 `.60` → logcat「会话已失效，后台静默重新登录」→ **9.09s** 完成 → cookie 换成 `.219`，health 首建，课表正常；
- B2 服务端构造失效后冷启动：main-resume 静默重登 **8.84s**，`.219→.40`；
- B3 有效会话点刷新：只有 `lastOkAt` 前移、`lastLoginAt` 不变 → 走业务成功路径，未重登；
- B4 失效后点刷新（`doWithAuth` 恢复）：自动重登 `.40→.53`，坏节点学习/`badRoutes` 持久化；
- 单飞：每次冷启动 MainActivity+ScheduleFragment 各触发一次预热，logcat 只有一对「失效→重登」日志。

> 本轮优化（UI 提示 / 坏节点衰减 / TTL 学习）因**真实账号登录预算已用满（12/12）**，未重跑真实账号 E2E；
> 新增逻辑由 10 个纯函数单测 + 6 个 Store 仪器化测试覆盖。UI 提示的实际视觉效果建议后续真机/模拟器手动触发一次确认。

## 5. 已知限制与后续可选

1. **预热只能减少等待，不能消除**：若用户刚回前台就立刻点刷新，仍需等预热协程完成（最多剩余 ~8s）；现已加"正在恢复登录…"提示缓解（不再像卡死）。
2. **TTL 学习只是上界估计**：只在观察到失效时更新，且被"实际存活超过上界"推翻会清除；从未失效过的节点仍用默认 25min 阈值。
3. **强制失效仍可能被误判为坏节点**：人工 logout/服务端清理发生在 10min 内时，该节点会被记入 `badRoutes`（现 7 天后自动失效，成本可控）。同节点互踢走 `kickout=1` 分支不会误标。
4. **不做后台保活**（有意）：离开 App 超过节点 TTL 后仍会过期，靠前台预热/重试恢复。
5. **UI 提示只在 RESUMED 页面展示**：若恢复发生时 App 在后台（少见），提示会被丢弃；失败提示仍由各调用方展示。
6. **密码明文存储、rememberMe 不可用、IP 变化影响**未在本次改造范围内（见实测报告限制章节）。
