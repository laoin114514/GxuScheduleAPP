# 踩坑：小组件重新构建安装后桌面「没有变化」

| 项目 | 内容 |
|---|---|
| 现象 | 重新构建 APK 并启动模拟器后，桌面上的「下一门课提醒」仍显示旧样式 |
| 日期 | 2026-10-02 |
| 环境 | Windows + Android Studio 模拟器（x86_64，Android 14+，Pixel Launcher），分支 `feat/widget` |
| 结论 | 两层问题叠加：① 安装后应用处于 stopped 状态收不到刷新广播；② 布局里用了 RemoteViews 白名单外的 `<View>` 导致整卡加载失败 |

---

## 一、现象与排查链路

重新构建并安装新包后，桌面小组件仍显示旧样式。逐层排查与实锤证据如下。

### 第 1 层：装上后不刷新（stopped 状态吞广播）

`adb install -r` 替换包后，系统会让应用进入 **stopped 状态**，此后发往它的所有广播（包括系统包替换后的组件更新、以及自定义 `ACTION_REFRESH`）都被丢弃。表现为：

- 桌面继续渲染**替换前缓存的 RemoteViews**（旧布局 + 旧数据）；
- `dumpsys appwidget` 里该 widget 的 `views=` 对象还是旧的（对象哈希不变）；
- logcat 里系统反复通知的是别的组件（如秒级 tick 的 Minimal/Schedule），唯独目标组件没有更新记录。

解决：**启动一次 App 解除 stopped 状态**，再触发刷新：

```bash
adb shell am start -n com.cherry.wakeupschedule/.MainActivity
adb shell am broadcast -a com.cherry.wakeupschedule.widget.next.ACTION_REFRESH \
    -n com.cherry.wakeupschedule/.widget.NextCourseWidgetProvider
```

若桌面仍显示旧内容但 `dumpsys appwidget` 中 `views=` 的对象哈希已变化（说明系统侧已持有新视图、只是桌面没重绘），重启桌面强制重绑定：

```bash
adb shell am force-stop com.google.android.apps.nexuslauncher   # Pixel Launcher
```

### 第 2 层：真正的代码 bug —— RemoteViews 白名单不允许裸 `<View>`

重启桌面后组件直接显示 **「Can't load widget」**，桌面进程日志给出实锤：

```
W AppWidgetHostView: Error inflating RemoteViews
W AppWidgetHostView: android.view.InflateException: Binary XML file line #60 in
    com.cherry.wakeupschedule:layout/widget_next_course: Error inflating class android.view.View
W AppWidgetHostView: Caused by: ... Class not allowed to be inflated android.view.View
```

**RemoteViews 的布局元素有白名单**（`@RemoteView` 注解类）：TextView / Button / ImageView / Chronometer / ProgressBar / LinearLayout / FrameLayout / RelativeLayout / GridLayout 等。**裸的 `<View>` 不在名单里**——本组件用 `<View>` 画 4dp 课程色竖线，导致整张卡片在桌面进程加载失败：

- 失败前桌面「看起来没变化」是旧 RemoteViews 兜底；
- 失败后（旧视图被清）就是「Can't load widget」。

**修复**：竖线改用白名单内的 `<FrameLayout>` 承载（`RemoteViews.setInt(id, "setBackgroundColor", color)` 反射调用对所有 View 子类生效，视觉零差异）：

```xml
<!-- RemoteViews 布局白名单不允许裸 <View>，色条用 FrameLayout 承载 -->
<FrameLayout
    android:id="@+id/bar_current"
    android:layout_width="4dp"
    android:layout_height="match_parent"
    android:layout_marginEnd="8dp"
    android:background="@color/widget_bar_neutral" />
```

> 排查这类问题最快的路径：`adb logcat` 按**桌面进程 pid** 过滤 `InflateException`（`pidof com.google.android.apps.nexuslauncher` 后 `logcat --pid=<pid>`），系统侧 `AppWidgetServiceImpl` 日志只负责"已通知"，加载失败只有宿主进程会报。

### 附带发现：Android 14+ 精确闹钟默认被拒（未修，另立项）

模拟器（targetSdk 35，Android 14+）上 `SCHEDULE_EXACT_ALARM` 默认不授予，每次 `setExactAndAllowWhileIdle` 都抛
`SecurityException: Caller ... needs to hold android.permission.SCHEDULE_EXACT_ALARM or ... USE_EXACT_ALARM`，
被 `scheduleNextTransitionUpdate` 的 try/catch 吞掉——**状态切换（进行中→下课→N 分钟后）的即时刷新在真机 Android 14+ 上同样会失效**，只能靠 15 分钟周期闹钟 / `updatePeriodMillis` / App 内分钟 tick 兜底。

- 模拟器临时解法：`adb shell appops set com.cherry.wakeupschedule SCHEDULE_EXACT_ALARM allow`
- 代码侧候选方案（另开工单）：改用 `USE_EXACT_ALARM`，或 `canScheduleExactAlarms()` 判断 + 降级 `setWindow` + 引导用户到 `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`。

## 二、小组件刷新快速命令（验证新样式用）

```bash
# 1. 构建
./gradlew :app:assembleDebug

# 2. 安装（拆包 ABI 需与设备一致，`adb shell getprop ro.product.cpu.abi` 查询）
adb install -r app/build/outputs/apk/debug/GxuScheduleAPP-debug-0.0.0-x86_64.apk

# 3. 启动一次 App 解除 stopped 状态（替换包后必须）
adb shell am start -n com.cherry.wakeupschedule/.MainActivity

# 4. 触发目标组件刷新
adb shell am broadcast -a com.cherry.wakeupschedule.widget.next.ACTION_REFRESH \
    -n com.cherry.wakeupschedule/.widget.NextCourseWidgetProvider

# 5. 仍显示旧视图时重启桌面（会重新绑定并按系统存储的 RemoteViews 重渲染）
adb shell am force-stop com.google.android.apps.nexuslauncher

# 诊断速查
adb shell dumpsys appwidget | grep -A6 "id=17"          # 看 views= 对象哈希是否变化
adb logcat --pid=$(adb shell pidof com.google.android.apps.nexuslauncher)   # 桌面端 InflateException
```

## 三、相关坑：改系统时间后小组件不立即刷新（TIME_SET 注册错字符串，2026-10-02 修复）

**现象**：手动改系统时间后，「下课倒计时」「今日课程概览」1 秒内刷新，而「下一门课提醒」要等 1~2 分钟。

**两层原因**：

1. **秒级 tick 只覆盖两个组件**（`App.kt` 秒级 `postDelayed` 只 triggerUpdate Minimal + Schedule，它们需要秒级倒计时）；下一门课提醒只有分钟级 `ACTION_TIME_TICK`（整分边界触发），改时间后最长要等约 1 分钟——这是设计内的时序差异。
2. **真 Bug：Manifest 里 `WidgetTimeChangedReceiver` 注册的 action 是 `android.intent.action.TIME_CHANGED`，而系统改时间广播的是 `android.intent.action.TIME_SET`**（`Intent.ACTION_TIME_CHANGED` 常量的值就是 `"android.intent.action.TIME_SET"`）——过滤器监听了一个系统永远不会发送的字符串，接收器从未在「改时间」时触发过（同文件 `DATE_CHANGED`/`TIMEZONE_CHANGED` 字符串正确，只有这条断）。

**排查实锤**：logcat 中每秒只有 id 15/19（秒级 tick）、id 17 仅整分出现；`adb shell am broadcast -a android.intent.action.TIME_SET` → id 17 无响应；`am broadcast -a android.intent.action.TIME_CHANGED`（假字符串）→ id 17 立即响应，证明接收器本身没问题、是过滤器挂错 action。

**修复**：Manifest 过滤器改为 `<action android:name="android.intent.action.TIME_SET" />`。

**经验**：Intent 常量与 Manifest 字符串是两套写法，`ACTION_TIME_CHANGED` ≠ `"android.intent.action.TIME_CHANGED"`；注册系统广播时必须以系统实际广播的字符串为准（可 `adb shell am broadcast -a <action>` 后看目标组件是否响应来隔离验证）。

## 四、经验小结

1. **替换安装后 App 是 stopped 状态**：任何广播（含系统组件更新）都收不到；先 `am start` 再发刷新广播。
2. **RemoteViews 布局只用白名单控件**：色条/占位用 `FrameLayout`（或 TextView/ImageView），不要写裸 `<View>`；这类错误本进程不报、只有宿主（桌面）报，且症状是「不刷新」或「Can't load widget」，极具迷惑性。
3. **诊断分区看**：`AppWidgetServiceImpl`（系统侧，推送是否发生）与 `AppWidgetHostView`（桌面侧，加载是否成功）要分开过滤。
4. **改时间不立即刷新**：先查秒级/分钟 tick 覆盖范围（`App.kt`），再查 `WidgetTimeChangedReceiver` 的 action 字符串是否为 `TIME_SET`（详见第三节）。
